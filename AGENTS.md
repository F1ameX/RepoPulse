# Разработка RepoPulse

Эти инструкции относятся ко всему репозиторию. Общайся с пользователем на русском.
Сохраняй существующие пользовательские изменения и ограничивай правки текущей задачей.

## Источники требований

- Основная архитектура — [документ №916](https://ai.nsu.ru/documents/916),
  задачи и спринты — [план №917](https://ai.nsu.ru/documents/917).
- [Локальное описание архитектуры](docs/architecture/repopulse_architecture.md)
  содержит ссылки на сценарии №888, профиль анализа №889 и методику №909.
- [Flow данных](docs/architecture/data-flow.md) описывает взаимодействия и бизнес-правила.
- [Контракты](contracts/README.md), [карта полей](docs/field-map.md) и
  [ошибки](docs/errors.md) задают формы запросов, ответов и внутренних сообщений.


## Общая структура backend
```text
/ca-template
├── /cmd                                 #
│   └── /<service_name>                   #
│       └── main.go                      # Точка входа в приложение
├── /migrations                          # Схемы БД, пользователи, миграции
├── /docs                                # Сваггеры, документация и т. д.
├── /internal                            # Внутренние пакеты
│   ├── /<service_name>                   #
│   │   ├── /adapter                     # Адаптеры
│   │   │   ├── /in                      # Входящие запросы в приложение
│   │   │   │   ├── /grpc                # Grpc хендлеры
│   │   │   │   ├── /http                # Http хендлеры
│   │   │   └── /out                     # Исходящие запросы приложения
│   │   │       ├── /<client_name>        # Другие клиенты
│   │   │       └── /repository          # Репозитории
│   │   ├── /app                         # Инициализация приложения
│   │   │   ├── app.go                   # Запуск приложения
│   │   │   ├── config.go                # Конфиг
│   │   │   └── init.go                  # Инициализация зависимостей
│   │   ├── /domain                       # Модели бизнес логики
│   │   └── /application                     # Точка входа в бизнес логику
│   │       ├── /<service-name>           # Доменная сущность
│   └── /pkg                             # Библиотеки, которые используются несколькими сервисами
│       └── /adapter                     # Общие адаптеры
│           ├── /in                      # Входящие общие адаптеры
│           └── /out                     # Исходящие общие адаптеры
│               ├── /<client_name>        # Общие клиенты
│               └── /repository          # Общие репозитории
├── /pkg                                 # Все экспортируемые компоненты
│   └── proto                            # Сгенерированные proto-файлы
```

## Структура и границы сервисов

В дереве выше `/ca-template` обозначает `project/backend`. Это целевая структура
backend: размещай новый код по ней, даже если существующий каркас пока неполон.
Перенос существующих пакетов выполняй в рамках задачи, которая их затрагивает.

- `project/backend` — Go; версия определяется go.mod. Точки входа:
  `cmd/api`, `cmd/auth`, `cmd/report`, `cmd/analyzer`.
- `project/frontend` — React, TypeScript, Vite; команды и зависимости в package.json.
- `contracts/{common,auth,analyzer,report,gateway}` — исходные спецификации по сервисам.
- `project/backend/migrations/{auth,analyzer,report}` — SQL по владельцам данных.
- `docs` — документация полей, архитектуры и движения данных.
- `project/backend/docs` — документация backend и Swagger-артефакты;
  исходные спецификации остаются в contracts, общая документация — в корневой docs.
- `project/backend/pkg` — экспортируемые компоненты;
  `pkg/proto` — сгенерированный protobuf-код.

API Gateway обрабатывает HTTP, получает проверенный контекст от Auth и передаёт
вызовы. Сканеры, расчёт метрик и Score размещаются в Analyzer.
Auth отвечает за идентичности и сессии. Analyzer — за очередь, сбор Git/GitHub/OSV,
пять анализаторов, 12 метрик, Score, рекомендации, объяснение и сохранение результата.
Report читает сохранённые отчёты и историю с проверкой доступа.

Внутри `internal/<service>` придерживайся разделения из дерева:

- `app` — запуск, конфигурация, инициализация зависимостей и жизненный цикл;
- `application/<service-name>` — сценарии и точка входа в бизнес-логику;
- `domain` — предметные модели и правила без зависимости от транспорта;
- `adapter/in/http` и `adapter/in/grpc` — входящие обработчики, вызывающие application;
- `adapter/out/<client_name>` — клиенты внешних сервисов;
- `adapter/out/repository` — реализации доступа к БД.

В `internal/pkg` размещай средства, используемые несколькими сервисами, сейчас
command и logger. Общие адаптеры размещай в `internal/pkg/adapter/in` и
`internal/pkg/adapter/out` по той же схеме. Внутренние пакеты не выноси в корневую pkg.

Интерфейсы зависимостей описывай по месту использования — в пакете-потребителе,
рядом с кодом, которому они нужны. Например, application объявляет нужный ему
интерфейс хранилища, а adapter/out/repository реализует его. Входящий HTTP/gRPC
обработчик при необходимости объявляет свой интерфейс вызываемых сценариев.
Ограничивай интерфейс нужными потребителю методами; не создавай отдельный общий
каталог interfaces и не добавляй интерфейс каждой структуре реализации.

Бизнес-логика не зависит от adapter и app. Конкретные реализации связываются
с потребителями в app/init.go; app не содержит сценарии application.
application использует domain и интерфейсы зависимостей; domain не зависит от application.

Используй общий `command.Execute`, логгер из контекста и завершение через context.
Настройки читаются из окружения процесса; новые параметры описывай в README и
`.env.example`. Автоматическая загрузка .env сейчас отсутствует.


Сейчас gRPC-методы объявлены для Auth и Report; analyzer.proto содержит сообщения,
а операции Analyzer описаны внутренним интерфейсом. При добавлении транспорта
обновляй контракты и flow, не объявляй несуществующие RPC готовыми.
Для GET /auth/session используется Auth.GetSessionContext; проверенный контекст
перед анализом получает Auth.ResolveContext. Не обходи Auth прямым чтением его
таблиц из Gateway. В С1 реализован гостевой путь; account register/login/logout
и получение сведений о действующем аккаунте остаются задачами следующих спринтов.

## Контракты и документация

- HTTP задаёт `contracts/gateway/v1/openapi.json`, JSON-модели — сервисные
  `v1/schemas.json`, бинарный gRPC — сервисные `.proto`.
- При изменении интерфейса синхронно обновляй соответствующие спецификации,
  примеры, `docs/fields`, карту полей, ошибки и затронутый flow.
- HTTP JSON использует snake_case. Не смешивай отсутствие поля, null, ноль,
  false и пустую строку; пустой список передавай как `[]` согласно схеме.
- Для присутствия скалярного protobuf-поля используй proto3 optional.
  Не добавляй scalar wrappers, json_name или ProtoJSON ради HTTP DTO:
  Gateway явно переносит поля между транспортными представлениями.
- Не переиспользуй опубликованные номера protobuf-полей; удалённые номера и
  имена резервируй через reserved. Несовместимые изменения требуют версии API.
- Код классов контрактов разработчики генерируют инструментами своих сервисов.
  Не добавляй общий Python-генератор, централизованную папку tools или Makefile.

В contracts описывай поля, ограничения интерфейсов, операции и ошибки.
Алгоритмы обработки, парсеры, лимиты источников и порядок выполнения описывай
в docs/architecture. Избегай дублирования подробных правил в нескольких местах.

На [диаграмме компонентов](docs/architecture/diagrams/components.md) показывай
сервисы и их связи: Analyzer — один блок. Его внутренние модули описываются
в flow. Используй полные названия сервисов вместо однобуквенных обозначений.
При изменении диаграммы обновляй соседний components.png.

## Данные и миграции

Сейчас используется одна PostgreSQL с отдельными схемами auth, analyzer, report.
Auth владеет идентичностями и сессиями; analyzer хранит отправки, очередь и снимки;
report — отчёты и просмотры истории. Analyzer публикует снимок, отчёт и completed
одной транзакцией. Не разделяй БД и не добавляй брокер в рамках несвязанной задачи.

Миграции — обычные SQL-файлы Goose с Up/Down для схем, таблиц и индексов.
Используй необходимые PK/FK, NOT NULL и UNIQUE. Валидация, переходы состояний и
прочая бизнес-логика остаются в сервисах; SQL-функции, триггеры и StatementBegin/End
для этого не нужны. Для уже применённых миграций добавляй следующие по номеру.

Порядок Up: auth → analyzer → report; Down — обратно.
В Docker Compose миграции применяет отдельный контейнер `migrations` после
готовности PostgreSQL; Auth и Analyzer ждут его успешного завершения.
У каждого каталога своя таблица версий Goose. Сами приложения не запускают
миграции. При запуске вне Compose разработчик применяет их через Goose CLI.
SQL-изменения проверяй на отдельной тестовой БД.
Подробности — в [README миграций](project/backend/migrations/README.md).

## Правила анализа

- MVP анализирует публичные GitHub-репозитории статически. Не исполняй код,
  тесты, сборку, Git hooks и команды установки зависимостей исследуемого репозитория.
- Owner определяется проверенным серверным контекстом и фиксируется при отправке;
  клиент не назначает владельца. Вход в аккаунт не переносит гостевые результаты.
- request_id относится к пользовательской отправке, trace_id — к диагностике.
  Повтор той же отправки не создаёт второе задание. Чтение статуса, отчёта и истории
  не запускает новый анализ.
- Сохраняй окно, версии, полноту источников и снимок для воспроизводимости.
  Не подменяй неизвестные значения нулями и не выдавай partial за полные данные.
- Score и рекомендации определяются методикой и каталогом. AI выбирает допустимое
  объяснение, не меняет оценки и действия; при сбое используется fallback.
- Не сохраняй и не логируй значения найденных секретов, пароли или токены.

Подробные условия актуальности отчёта, состав снимка, лимиты и профили зависимостей
бери из действующих документов и flow, без собственных упрощений методики.

## Frontend

Подключай API по OpenAPI. Существующие локальные типы и repositoryService ещё
содержат расхождения с текущими контрактами; не используй их как источник требований.
При интеграции исправляй соответствующий участок клиента вместе с его моделями.
Frontend отображает готовый результат, не пересчитывает Score и не придумывает
проценты выполнения. Вызовы API размещай в services, UI — в pages/компонентах.

## Проверки изменений

Для backend выполняй из `project/backend`:

```sh
gofmt -l .
go vet ./...
go test -race ./...
go build ./...
```

Применяй gofmt к изменённым Go-файлам; вывод проверки форматирования должен быть пустым.
Для frontend из `project/frontend`: `npm run lint` и `npm run build`.
При изменениях контрактов проверяй синтаксис, ссылки схем, совместимость JSON/protobuf
и примеры затронутых моделей. Не считай проверку схем доказательством готовности сервиса.
Для изменений только документации достаточно проверить ссылки, оформление и diff.

Добавляй тесты на значимое поведение и исправляемые ошибки, без тестов-пустышек.
Перед завершением проверь `git diff --check`. Сообщай, что изменено, какие проверки
прошли и что осталось непроверенным; не заявляй о готовности заглушек и не скрывай сбои.
