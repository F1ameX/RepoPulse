### Выбрать и описать методы расчёта Repo Health Score для MVP
Целью данного документа является обоснование выбранного метода для расчета оценки здоровья репозитория для MVP RepoPulse. Решение основано на результатах исследования подходов к оценке и сформированных ранее гипотез о категориях и метриках. Согласны ли с этим?
### 2. Критерии выбора метода для MVP

- объяснимость итоговой оценки - пользователь должен понимать, как каждая метрика влияет на итоговый балл.
- доступность исходных данных - метрики должны использовать только доступные данные (через стандартные API GitHub/GitLab, git clone), без необходимости обращаться к сторонним сервисам (SAST и др.).
- воспроизводимость результата - одинаковый снимок репозитория в одно и то же время должен давать один и тот же score.  
- независимость от большой обучающей выборки - в нашем случае отсутствует готовый размеченный датасет репозиториев, что делает обучение ML-модели неприменимым подходом для MVP.
- возможность реализации в рамках проекта - метод должен быть эффективным и реализуемым в рамках проекта.
- поддержка GitLab и GitHub - унифицированный подход к данным где это возможно.
- устойчивость к отсутствию части данных - отсутствие каких-то данных, используемых в подсчетах метрик не должно автоматически обнулять оценку.

### 3. Выбор подхода к расчету Repo Health Score для первой версии продукта

На основе исследования scoring-approaches-research выбран гибридный подход, основанный на взвешенном среднем с пороговыми правилами и системой комплексных рисков.
Обоснования выбора: 
1. в scoring-approaches-research.md (п. 3.6) сказано, что единой обучающей выборки, описывающей здоровье репозитория нет. Следовательно, обучение модели на разрозненных отдельно взятых данных откладываются для прогнозирования отдельных событий.
2. взвешенное среднее (описание в п. 2.1) позволяет прозрачно объединить 9 категорий, вклад каждой категории будет понятен.
3. пороговые правила и комплексные риски (п. 2.3, п. 2.6) позволяют учитывать контекст. Комплексные сигналы помогают решить проблему, когда хорошее среднее скрывает одну критическую проблему.
4. отказ от геометрического среднего (п. 2.4): поскольку наличие хотя бы одного нулевого балла обнуляется весь результат. Возможно в MVP некоторые метрики будут выражаться характеристической функцией (то есть возможно наличие нуля).
5. роль AI (п. 4) состоит в генерации понятных текстовых объяснений и рекомендаций на основе уже посчитанных фактов и сработавших правил. 

### 4. Описание выбранного подхода
##### 4.1. категории оценки
Используются 9 категорий из `repository-health-hypotheses.md`. Веса являются стартовой гипотезой и будут калиброваться:

1. Активность и регулярность (15%)
2. Распределение изменений (15%)
3. Безопасность (15%)
4. Документация (10%)
5. Тестирование (10%)
6. Зависимости (10%)
7. CI/CD (10%)
8. Структура и организация (10%)
9. Версионирование и релизы (5%)
##### 4.2.  используемые показатели
Используемые показатели перечислены в следующем файле: repository-health-hypotheses.md
##### 4.3. нормализацию показателей
Сырые метрики переводятся в баллы категории $S_i \in [0, 100]$ с помощью непрерывных функций (без резких скачков): линейная нормализация (если есть четкий порог), логарифмическая (для метрик "чем больше, тем лучше" с эффектом насыщения), экспоненциальный спад (для метрик "чем меньше, тем лучше), долевая (для процентов и долей)
##### 4.4. способ объединения показателей в итоговую оценку
Расчет происходит в два этапа.
Этап 1: базовый score (взвешенное среднее): $S = \frac{w_{1}s_{1} + \cdots  + w_{n}s_{n}}{w_{1} + \cdots  + w_{n}}$
Этап 2: применение комплексных рисков: если срабатывают комплексные сигналы, то фиксируется реализованный риск (необходимо предусмотреть понятную обработку данного риска, например, выводить информацию в UI).

Данное решение снизить риск "наказать" проект дважды за один и тот же показатель. Также при наличии системы штрафов объяснимость итоговой оценки для пользователя была бы существенно сложнее, что излишне для MVP.  Полностью следует рекомендации из scoring-approaches-research.md (п. 2.6)
##### 4.5. обработку отсутствующих данных
Согласно исследованию scoring-approaches-research отсутствие данных не означает автоматически плохое состояние.
Однако если метрика не может быть рассчитана из-за недоступности показателя, ей присваивается статус N/A. Она исключается из расчета балла категории Si. Веса внутри категории перенормируются на оставшиеся доступные метрики. В UI обязательно нужно уведомить пользователя о "полноте покрытия" метрик, чтобы он имел в виду, что определенные метрики не смогли быть посчитаны.
##### 4.6. отображение причин снижения Score
1. Вклад каждой из 9 категорий в итоговый балл.
2. Список сработавших комплексных сигналов, то есть явное указание на риски.
3. Детализация по метрикам и возможность посмотреть конкретные факты по показателям.

### 5. Методы и показатели, отложенные на последующие версии

Отложенные методы:
- ML для общего score: до появления размеченной выборки RepoPulse, поскольку существующие датасеты (GHALogs, First Response Latency, DeepPull) описывают отдельные процессы, а не общее здоровье.
- геометрическое среднее: хорошо штрафует за слабые категории, однако наличие хотя бы одного нулевого балла обнуляет весь результат. В рамках MVP многие данные могут отсутствовать (N/A), что создает риск несправедливого обнуления.
- AHP: требует большого количества экспертных оценок (для 9 категорий нужно 36 парных сравнений), веса должны быть объективны.
- TOPSIS - требует определения лучшего и худшего (группы сравнений), результат целиком зависит от выбранных эталонов.
- EWMA - отложено до накопления исторических данных в базе RepoPulse.
- Классификация (ML для отдельных событий): отложен в рамках MVP до реализации расчета общего Score
- Кластеризация (k-means): хороший вариант для проверки преимущества данного подхода при разделении проектов по назначению, размеру проекта и тд

Отложенные метрики:
При повторном рассмотрении было решено отложить реализацию  метрики "Актуальность документации относительно кода" (категория: Документация), поскольку на данном этапе не совсем понятно как корректно ее считать и интерпретировать.

Также было решено отказать от метрики "Доля self-merge" (категория: Распределение изменений между участниками), поскольку она меньше отражает суть чем метрика, выражающая долю независимых review.

Метрика "Базовая структура репозитория" (категория: Структура и организация репозитория) - упирается в отсутствие универсальной структуры репозитория, поэтому не является показательной и реализуемой - решено было отказаться. 

### 6. Предлагаемые формулы для расчета каждой метрики и каждой категории: 

Каждая сырая метрика $x_i$ преобразуется в $m_j$, $m_j \in [0,100]$. Затем считается score категории $S_i = \frac{\sum_{j \in A_i} w_{ij}*m_{ij}}{\sum w_{ij}}$, где 
$S_i$ - score i-ой категории,
$A_i$ - доступные метрики категории (некоторые могут быть недоступны, они не учитываются),
$m_{ij}$ - нормализованная на прошлом шаге метрика,
$w_{ij}$ - вес метрики (на данном этапе числа взяты из предположений).

Далее, для Health Score высчитывается взвешенное среднее.

Предложенные веса являются всего лишь стартовой конфигурацией, поскольку эмпирической выборки у нас нет, следовательно мы не можем утверждать, что данное соотношение объективно правильно. Повышенный вес назначен активности, распределению изменений и безопасности, поскольку эти категории характеризуют поддерживаемость и устойчивость процесса разработки. 

4 типа нормализации: 
- линейная (равномерно)
- логарифмическая (сильно растет в начале, к концу выходит на плато, насыщение)
- экспоненциальная (маленькие значения не меняются, большие - взрыв)
- долевая (вклад в целое)
### Активность и регулярность (15%)

##### Частота коммитов (берем неделю)
Считаем среднюю частоту коммитов в неделю. 
Можно использовать логарифмическую нормализацию для того чтобы 30 коммитов не имели большего значения чем, например, 12 коммитов. Поскольку количество коммитов является показателем активности. 

$m_{commits} = \frac{ln(1+x)}{ln(1 + max)}$
$M_{commits} = 100 * min(1, m_{commits})$

max - количество коммитов, после которого score прирост затухает.
Предложено: max = 10
##### Дни с последнего коммита
Нужна некоторая затухающая нормализация, следовательно подходит экспоненциальная: 
$M_{last} = 100 * e^{-days/k}$

k - некоторая константа, за k дней score снижается до 37
Предложено: k = 30
Месяц без коммитов - сигнал, но не катастрофа.

##### Изменение активности во времени
Сравнивать придется периодами, следовательно необходимо выбрать длительность периода. Также необходимо выбрать длительность наблюдаемого периода, поскольку изменения активности всего репозитория отследить тяжелее, если репозиторию 7-10 лет (если репозиторий моложе, соответственно брать их возраст в месяцах).

Берем сырые значения: $C_1, ..., C_p$, где p - наблюдаемый период, $C_i$ - кол-во коммитов за период.

$m = \frac{\sum^{p} i*C_i}{\sum^{p} i * C_{i-1}}$, то есть берем среднее взвешенное, где веса равны номеру месяца (от 1 до p по их количеству), для того чтобы актуальная активность больше влияла на результат.

Полученная $m \in [0, +inf)$, теперь переводим в шкалу $[0,100]$. Стоит учитывать, что стабильный проект это все еще показатель здорового репозитория, поэтому предлагается ввести три константы: $M_{0}$ - кол-во баллов для стабильного проекта, константа s считается 
$s = \frac{1}{2}ln(\frac{M_0}{100 - M_0})$,
k - на сколько должна вырасти активность, чтобы получить максимум (например, 1.5 - рост активности на 50% дает 100 баллов)

Тогда общая метрика: $M_{trend} = 50 + 50*tanh(\frac{ln R}{ln k} + s)$ 

Предложено: 
$M_0$ = 80 (балл за стабильный проект, стабильность хорошо, но не идеально)
k = 1.2 (рост на 20%, умеренный рост довольно реалистичная цель)
p = 6 (длительность наблюдаемого периода, 6 месяцев это достаточно для выявления тренда)

$S_{activity}​=0.35⋅M_{commits}​+0.35⋅M_{last}​+0.30⋅M_{trend}$​
### Распределение изменений между участниками (15%)

##### Доля крупнейшего участника
$M_{concentration} = 100(1 - p_{max})$, где $p_{max}$ - доля изменений крупнейшего участника.

$p_{max} = \frac{max_i x_i}{\sum_{i} x_i}$ (самое большое кол-во коммитов от 1 участника к сумме вкладов каждого участника)

Однако для 1 разработчика при такой формуле результат равен 0 - неправильно. Следовательно,
считаем только если $N_{active}$(кол-во активных участников) > 1, если $N_{active}$ = 1 тогда $M_{concentration} = 100$

##### Качество ревью (кол-во уникальных активных ревьюеров + кол-во PR  с независимыми ревью + кол-во + время до первого ответа ревьюера)

$M_{review} = w_1M_{reviewers} + w_2M_{independent} + w_3M_{response}$

Кол-во ревьюеров: $M_{reviewers} = 100 * min(1, \frac{R}{d})$, где R - среднее кол-во ревьюеров на PR. Константа d - кол-во ревьюеров, определяющих точку насыщения (сколько уже хорошо).

Независимое ревью: $M_{independent} = 100 * \frac{N_{independent PR}}{N_{PR}}$
то есть кол-во PR где ревьюер не автор к общему кол-ву PR.

Время до первого ревью: $M_{response} = 100*e^{-t/k}$
t - среднее время до первого ревью (в чем измеряется время),
k - параметр чувствительности (время к которому балл падает до 37)

Предложено: 
d = 2 (точка насыщения, два ревьюера - достаточно)
k = 48 (время, к которому балл падает до 37, 48 часов достаточное время для получения первого ответа даже с учетом поясов)

$S_{distribution}​=0.25⋅M_{concentration}​+0.75⋅M_{review}$​

$N_{available}$ - сколько есть файлов, в знаменателе соответственно сколько нужно
$N_{all}$ = 3 (LICENSE, CONTRIBUTING, CODE_OF_CONDUCT)

$M_{testing}$ = 100, если есть

### Зависимости (10%)
##### Устаревшие зависимости
$p_{old} = \frac{N_{old}}{N_{dependencies}}$ 
тогда метрика $M_{fresh depend} = 100 * (1 - p_{old})$ 
##### Автоматизация
$M_{auto}$ = 100, если есть Dependabot/Renovate
$M_{auto} = 0$, если их явно нет

### Безопасность (15%)
##### Уязвимости в зависимостях
Лучше считать: 
$Risk = w_1N_{crit} + w_2N_{high} + w_3N_{medium} + W_4N_{low}$
$M_risk = 100 * e^{-Risk/k}$

k - значение Risk падает до 37, чем больше k - тем мягче оценка. Выбирается так: если Risk = 10 это плохо и score 37 => k = 10, если Risk = 10 должен давать score 70, то k около 30 (пример).

Предложено: 
k = 15
w1 = 10, w2 = 5, w3 = 2, w4 = 1

##### Потенциально опасные данные 
$M_{secret}$ = 100, если нет
$M_{secret} = 50$, если есть потенциальные утечки данных
$M_{secret} = 0$, если есть действительные утечки данных
$M_{secret} = N/A$, если нет данных

$S_{security}​=0.50⋅M_{risk}​+0.35⋅M_{secret}​+0.15⋅M_{sast}​$

##### SAST
$M_{sast}$ = 100, если есть
$M_{sast} = 0$, если явно нет
$M_{sast} = N/A$, если нет данных


### CI/CD (10%)
##### Запуск в CI
$M_{ci}$ = 100, если есть
$M_{ci} = 0$, если явно нет
##### Доля успешных тестов
$M_{success} = 100 * \frac{N_{success}}{N_{completed}}$ 
Отменённые/пропущенные запуски не должны автоматически считаться проваленными.
##### Защита основной ветки (обязательные проверки)
$M_{sast}$ = 100, если есть
$M_{sast} = 0$, если явно нет

То есть сверху мы фильтруем теги обычной регуляркой (например)
Если тегов нет, то тогда проект либо не использует, либо просто пока слишком молодой - используем N/A.
##### Releases notes
$M_{notes}$ = 100, если есть releae notes
$M_{notes} = 0$, если есть релизы, но нет notes

$M_{gitignore}$ = 100, если есть
$M_{gitignore} = 0$, если нет

$M_{artifacts} = 100*\frac{N_{present}}{N_{all}}$
N_all - нужно выбрать какие конкретные файлы мы будем проверять
N_all = 4 (`.env`, `node_modules/`, `dist/`, `*.log`)

$S_{structure}​=0.40⋅M_{gitignore}​+0.60⋅M_{artifacts}$​

## Как работать с N/A
Если какая то метрика вернула N/A это не означает автоматически что репозиторий плох. В таких случаях мы просто пересчитываем общее взвешенное среднее для категорий (на нижнем этапе с метриками так же).

Однако можно было бы добавить полноту обозревания: а именно в процентах показать сколько метрик было получено к полному кол-ву метрик. Тогда пользователю будет проще ориентироваться в полноте полученной оценки.

## Комплексные сигналы
Комплексные сигналы, предложенные в repository-health-hypotheses.md не стоит учитывать в score, поскольку это уже будет двойной штраф за один показатель. Но их можно использовать в качестве детекторов риска (допустим в UI предупреждать что вот, о наличии данного риска у репозитория).

## Рекомендации 
Рекомендации предлагается формировать в два этапа. На первом этапе детерминированный сервис рекомендаций (ну не совсем) сопоставляет подтверждённые найденные проблемы с заранее определённым каталогом правил рекомендаций. 
Для каждого правила задаются условие применения, основание, действие, ожидаемый эффект, приоритет и сложность реализации. 
На втором этапе LLM используется для преобразования структурированного набора фактов и выбранного действия в понятную для пользователя текстовую рекомендацию. LLM не определяет Score, не устанавливает наличие проблемы и не может добавлять новые действия или факты.


## Каталог проблем и детерминированных действий

Каталог строится только на показателях, используемых в Score. Низкий непрерывный показатель сам по себе не означает наличие проблемы: проблема фиксируется при достижении заданного порога `T`. Пороговые значения являются параметрами калибровки MVP. `N/A` не считается проблемой.

|Категория|ID проблемы|Условие|Действие|
|---|---|---|---|
|Активность|`LOW_COMMIT_ACTIVITY`|`M_commits < T_commits`|Поддерживать регулярные изменения|
||`STALE_REPOSITORY`|`M_last < T_last`|Проверить актуальность проекта и выполнить необходимые обновления|
||`ACTIVITY_DECLINE`|`M_trend < T_trend`|Проверить причины снижения активности и восстановить регулярность|
|Распределение изменений|`HIGH_CHANGE_CONCENTRATION`|`M_concentration < T_concentration` и `N_active > 1`|Распределить разработку между несколькими участниками|
||`LOW_REVIEWER_PARTICIPATION`|`M_reviewers < T_reviewers`|Назначить дополнительных ревьюеров для PR/MR|
||`LOW_INDEPENDENT_REVIEW`|`M_independent < T_independent`|Настроить обязательное независимое ревью|
||`SLOW_REVIEW_RESPONSE`|`M_response < T_response`|Сократить время до первого ревью|
||`NO_BRANCH_PROTECTION`|`M_protection = 0`|Включить обязательное ревью для основной ветки|
|Документация|`MISSING_README`|`M_readme = 0`|Добавить README с описанием проекта и инструкцией по запуску|
||`INCOMPLETE_SUPPORTING_DOCS`|`M_support < T_support`|Добавить отсутствующие сопровождающие документы|
||`STALE_DOCUMENTATION`|`M_fresh < T_fresh`|Обновить документацию в соответствии с кодом|
|Тестирование|`NO_TESTS`|`M_testing = 0`|Добавить автоматические тесты для основного кода|
|Зависимости|`OUTDATED_DEPENDENCIES`|`M_fresh_depend < T_dependency`|Обновить устаревшие зависимости|
||`NO_DEPENDENCY_AUTOMATION`|`M_auto = 0`|Настроить автоматическое обновление зависимостей|
|Безопасность|`DEPENDENCY_VULNERABILITIES`|`Risk > 0`|Обновить или заменить уязвимые зависимости|
||`POTENTIAL_SECRET_LEAK`|`M_secret = 50`|Удалить чувствительные данные из репозитория и заменить их безопасной конфигурацией|
||`SECRET_LEAK`|`M_secret = 0`|Удалить секрет из репозитория и заменить скомпрометированный секрет|
||`NO_SAST`|`M_sast = 0`|Подключить статический анализ безопасности|
|CI/CD|`NO_CI`|`M_ci = 0`|Настроить CI для автоматической проверки изменений|
||`LOW_CI_SUCCESS_RATE`|`M_success < T_success`|Исправить причины неуспешных CI-запусков|
||`NO_REQUIRED_CI_CHECKS`|обязательные CI-проверки не настроены|Сделать необходимые CI-проверки обязательными для основной ветки|
|Версионирование и релизы|`INVALID_VERSION_TAGS`|`M_semver < T_semver`|Привести версионные теги к единому формату|
||`MISSING_RELEASE_NOTES`|`M_notes = 0`|Добавлять release notes при публикации релизов|
|Структура|`MISSING_GITIGNORE`|`M_gitignore = 0`|Добавить `.gitignore` для используемого стека|
||`MISSING_PROJECT_FILES`|`M_artifacts < T_artifacts`|Добавить отсутствующие служебные файлы|
