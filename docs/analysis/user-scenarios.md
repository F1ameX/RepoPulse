# Пользовательские сценарии и функциональные требования RepoPulse

Редакция: 2.3 от 17.10.2026.
Задача анализа: [#17655](https://ai.nsu.ru/issues/17655).
Ответственный аналитик: Константин Мельников.
Публикация: [документ №888](https://ai.nsu.ru/documents/888).
Статус редакции: подготовлена для проверки; повторное согласование с frontend/UX не зафиксировано.

## 1. Назначение и основания

Документ определяет пользовательское поведение MVP RepoPulse: гостевой анализ, регистрацию и вход по логину/паролю, ввод репозитория, получение и просмотр результата, обработку ошибок и работу с историей отчётов. Раздел 6 содержит самостоятельные функциональные требования к наблюдаемым действиям системы, а не задачи разработчикам, ограничения технологий или внутренние API-контракты.

Основания:

- [Vision RepoPulse](https://ai.nsu.ru/documents/871) — назначение продукта, аудитория и объяснимый Repo Health Score от 0 до 100.
- [Задача #17655](https://ai.nsu.ru/issues/17655) — состав сценариев и результатов анализа.
- [Методические указания КРПО](https://ai.nsu.ru/documents/79), [общие методические указания, раздел 3](https://ai.nsu.ru/documents/363), [DEMO PROJECT](https://ai.nsu.ru/projects/pmdemo/issues) — самостоятельные Requirement, ответственный аналитик, связи Related to и словарь Wiki.
- Подтверждённые командные решения от 28.09.2026, переданные при уточнении этой задачи: в MVP только GitHub; обязательные и дополнительные направления анализа; история в профиле; повторное использование отчёта при отсутствии изменений.
- Вариант Андрея Иванова из [FR-27, #18351](https://ai.nsu.ru/issues/18351), выбранный при уточнении 17.10.2026: гостевой анализ без аккаунта; регистрация и вход по логину/паролю; история только для аккаунта; гостевые отчёты не переносятся в историю при входе.
- [Исследование показателей](https://ai.nsu.ru/documents/886) и [исследование платформенных данных](https://ai.nsu.ru/documents/889) — необходимость фактов, контекста и явного отражения неполноты данных.
- [Предложение по методу расчёта Score](https://ai.nsu.ru/documents/909) — контекст дальнейшего проектирования. Его гипотетические веса, формулы и нерешённые вопросы не устанавливаются этой спецификацией.

Vision описывает более широкий продукт. Указанные командные решения уточняют объём MVP; исследовательские предложения сами по себе этот объём не расширяют. Новая редакция заменяет прежний перечень FR-01–FR-15 целиком. Совпадение номера с прежней редакцией не означает сохранение прежнего содержания.

## 2. Границы и пользователи

### 2.1. Границы MVP

Авторизованный или неавторизованный пользователь указывает URL публичного репозитория GitHub. Выбора платформы в MVP нет. RepoPulse анализирует доступные данные и показывает отчёт; он не изменяет репозиторий и не исправляет найденные проблемы самостоятельно.

Обязательные направления: история изменений, документация, наличие тестов, конфигурация и доступные результаты CI/CD, безопасность данных. Зависимости, версионирование, pull requests и code review — дополнительные направления, не являющиеся условием приёмки базового MVP. Обязательное направление должно присутствовать в отчёте даже при недоступности его данных; это не обязывает выводить выдуманный балл.

Вне данной спецификации: приватные репозитории, ввод личного GitHub-токена, другие платформы, автоматическое исправление кода, постоянный мониторинг, интеграции с трекерами, формулы Score и алгоритмы рекомендаций. Регистрация и вход используют логин и пароль RepoPulse. Восстановление пароля и вход через GitHub в данной спецификации не описываются.

### 2.2. Целевые пользователи

| Группа аудитории | Цель использования |
|---|---|
| Разработчик, владелец репозитория | Найти технические проблемы и выбрать следующие улучшения |
| Технический руководитель | Получить первичную оценку незнакомого или давно не проверявшегося проекта |
| Участник open-source-проекта | Понять состояние проекта перед использованием или вкладом |
| Преподаватель, проверяющий | Получить единообразную первичную оценку учебного проекта |

Это группы аудитории, а не разные роли доступа. Для них предусмотрен один сценарий анализа. Score не заменяет экспертную оценку, code review или аудит безопасности.

[Неавторизованному пользователю](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) доступны анализ публичного репозитория и просмотр собственного результата в действующей гостевой сессии, а также регистрация и вход по логину/паролю. [Авторизованному пользователю](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) дополнительно доступны собственный профиль и история отчётов аккаунта. Вход в аккаунт не переносит гостевые отчёты в его историю. Система определяет владельца по проверенной сессии; другая сессия или аккаунт не получают доступ к чужим результатам, в том числе по прямой ссылке или запросу.

## 3. Пользовательские сценарии

### UC-05. Войти в аккаунт RepoPulse

**Актор:** неавторизованный пользователь.
**Цель:** получить доступ к профилю и истории своего аккаунта.
**Предусловие:** существует учётная запись RepoPulse с логином и паролем.
**Триггер:** неавторизованный пользователь выбирает «Войти».

1. Система показывает поля «Логин», «Пароль» и действие «Войти»; пароль скрыт при вводе.
2. Неавторизованный пользователь вводит логин и пароль и отправляет форму.
3. Система проверяет непустые поля и соответствие пары логин/пароль существующей учётной записи.
4. При успешном входе система определяет аккаунт по проверенной сессии и предоставляет доступ к его истории.

**Постусловие:** неавторизованный пользователь стал авторизованным. Гостевые отчёты не добавлены в историю аккаунта; новый анализ не запущен.

### UC-06. Зарегистрировать аккаунт RepoPulse

**Актор:** неавторизованный пользователь.
**Цель:** создать аккаунт для последующего входа и работы с личной историей.
**Предусловие:** открыта форма регистрации.
**Триггер:** неавторизованный пользователь выбирает «Зарегистрироваться».

1. Система показывает поля «Логин» и «Пароль»; пароль скрыт при вводе.
2. Неавторизованный пользователь заполняет поля и отправляет форму регистрации.
3. Система проверяет непустые значения и отсутствие аккаунта с таким логином.
4. Система создаёт аккаунт и сообщает об успешной регистрации.

**Постусловие:** создана учётная запись. Регистрация сама по себе не создаёт отчёт; для входа используется UC-05.

### UC-01. Получить оценку репозитория

**Актор:** авторизованный или неавторизованный пользователь RepoPulse.
**Цель:** понять состояние публичного репозитория и следующие действия.
**Предусловие:** открыта форма анализа; авторизованный или неавторизованный пользователь располагает URL репозитория.
**Триггер:** авторизованный или неавторизованный пользователь выбирает «Анализировать».

1. Система показывает поле URL и сообщение о поддержке публичных репозиториев GitHub.
2. Авторизованный или неавторизованный пользователь вводит URL и запускает проверку.
3. Система проверяет формат, поддерживаемую платформу и доступность публичного репозитория.
4. Система определяет владельца по проверенной сессии: аккаунт авторизованного пользователя либо гостевая сессия неавторизованного пользователя. Она проверяет наличие доступного этому владельцу актуального отчёта для репозитория.
5. Если актуального отчёта нет, система принимает новый анализ и показывает его идентификатор и состояние.
6. Авторизованный или неавторизованный пользователь наблюдает ожидание или выполнение анализа.
7. По завершении система открывает итоговый отчёт. Результат анализа авторизованного пользователя сохраняется в истории аккаунта; гостевой результат доступен только исходной действующей гостевой сессии.
8. Авторизованный или неавторизованный пользователь видит, что анализировалось, общий Score, оценки категорий, объяснения, проблемы, рекомендации и ограничения результата.

**Постусловие:** авторизованный или неавторизованный пользователь видит результат завершённого анализа либо явное сообщение о невозможности получить его. Неуспешный анализ не выдаётся за готовый отчёт.

### UC-02. Проверить репозиторий повторно

**Актор:** авторизованный или неавторизованный пользователь.
**Предусловие:** для репозитория есть отчёт, принадлежащий текущему аккаунту или действующей гостевой сессии.
**Триггер:** авторизованный или неавторизованный пользователь снова отправляет URL на анализ.

1. Система проверяет доступность репозитория и актуальность предыдущего результата.
2. Если подтверждено, что используемые данные, период оценки и методика не изменились, система открывает прежний отчёт с исходной датой и пояснением о повторном использовании.
3. Если обнаружены изменения или актуальность нельзя подтвердить, система запускает новый анализ по UC-01.

**Постусловие:** неизменившийся актуальный результат не дублируется; новый результат аккаунта не перезаписывает его историю. Гостевой результат остаётся в контексте своей сессии.

### UC-03. Открыть сохранённый отчёт

**Актор:** авторизованный пользователь в своём профиле.
**Предусловие:** вход выполнен; система определила профиль по действующей сессии.
**Триггер:** авторизованный пользователь открывает раздел «История отчётов».

1. Система показывает отчёты профиля от новых к старым либо сообщение о пустой истории.
2. Авторизованный пользователь выбирает отчёт по репозиторию и дате анализа.
3. Система открывает сохранённый результат именно выбранного анализа, не запуская новый.
4. Если авторизованный пользователь хочет получить текущую оценку, он выбирает «Проверить снова»; выполняется UC-02.

**Постусловие:** доступен исторический результат с его исходной датой, а не автоматически подменённая текущая оценка.

### UC-04. Разобраться в оценке и выбрать улучшения

**Актор:** авторизованный или неавторизованный пользователь, просматривающий готовый отчёт.
**Цель:** понять основания оценки и определить действия.
**Предусловие:** отчёт доступен авторизованному или неавторизованному пользователю.
**Триггер:** авторизованный или неавторизованный пользователь открывает результат анализа.

1. Авторизованный или неавторизованный пользователь читает общий Score и его объяснение.
2. Выбирает категорию и просматривает её оценку и показатели.
3. Проверяет факты: значения, период наблюдения и доступные ссылки на источники.
4. Просматривает обнаруженные проблемы и связанные рекомендации.
5. Учитывает отмеченные ограничения и принимает собственное решение о дальнейшей работе.

**Постусловие:** авторизованный или неавторизованный пользователь может проследить связь «данные — вывод — предлагаемое действие»; RepoPulse не сообщает о выполненном исправлении.

## 4. Что приложение показывает авторизованному и неавторизованному пользователям

| Часть результата | Обязательная информация |
|---|---|
| Объект анализа | GitHub, владелец и имя репозитория, ссылка, анализируемая ветка и commit SHA при наличии, дата и время анализа |
| Общий результат | Repo Health Score в диапазоне 0–100, объяснение основных факторов; при невозможности расчёта — явное отсутствие оценки с причиной |
| Категории | Название, рассчитанный балл или состояние отсутствия данных, объяснение; все пять обязательных направлений присутствуют |
| Основания оценки | Название показателя, значение и единица, период и размер выборки для агрегатов, использованное правило/порог при наличии, факт и доступный источник |
| Проблемы | Название, категория, описание, критичность, основание и возможное последствие; при пустом списке — сообщение с оговоркой об охвате проверки |
| Рекомендации | Предлагаемое действие, основание, ожидаемый эффект и приоритет; связь с проблемой или наблюдением |
| Ограничения | Какие данные отсутствуют, частично получены или неприменимы, почему и какие выводы ограничены |
| История профиля (только авторизованному пользователю) | Репозиторий, дата анализа, общий Score или отметка о его отсутствии, открытие выбранного результата и повторная проверка |

Состав собственного отчёта одинаков для авторизованного и неавторизованного пользователя. История аккаунта гостевой сессии недоступна. Это пользовательский состав результата, не JSON-схема. Адреса API, маршруты экранов, технические коды ошибок, интервал опроса и способ хранения выбираются при проектировании и не являются функциональными требованиями этой задачи.

## 5. Состояния взаимодействия

| Состояние | Что отображается | Действия |
|---|---|---|
| Вход / регистрация (неавторизованный пользователь) | Поля Логин и Пароль | Войти; зарегистрироваться; вернуться к гостевому анализу |
| Ошибка входа / регистрации (неавторизованный пользователь) | Причина ошибки; доступ к аккаунту не предоставлен | Исправить ввод; повторить; продолжить гостевой анализ |
| Ввод | Поле URL, поддерживаемая платформа | Анализировать |
| Проверка запроса | Проверяется URL/доступность/актуальность | Ожидать; повторная отправка той же формы блокируется |
| Ожидание | Анализ принят, его идентификатор | Проверить статус |
| Выполнение | Анализ выполняется; этап, если известен | Проверить статус |
| Успешное завершение | Переход к отчёту этого анализа | Просмотреть результат |
| Ошибка анализа | Причина и идентификатор анализа | Повторить; изменить URL |
| Ошибка связи | Статус временно неизвестен; последнее подтверждённое состояние | Повторить проверку того же анализа |
| Готовый отчёт | Собственный результат, исходная дата, ограничения | Изучить категории; проверить снова; авторизованному пользователю — открыть историю |

Состояния анализа и просмотра собственного отчёта доступны обоим типам пользователей. Для неавторизованного пользователя система использует гостевую сессию, для авторизованного — аккаунт. При утрате сессии существующего результата применяется A-14; история аккаунта требует входа (A-16).

Все требования связаны с #17655 отношением Related to, не являются её подзадачами и не содержат трудозатрат. Содержание блоков переносится в Description требований без изменения нормативного текста.

### FR-01. Ввод и проверка URL репозитория

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Условие: открыта форма нового анализа.

1. Система должна предоставлять поле «URL репозитория», действие «Анализировать» и пояснение «Поддерживаются публичные репозитории GitHub».
2. При отправке система должна удалить внешние пробелы и принять HTTPS-ссылку вида https://github.com/owner/repository с непустыми owner и repository. Завершающий слеш и суффикс .git допускаются и относятся к тому же репозиторию. Ссылки на файл, ветку или pull request, ссылки с учётными данными, другой схемой, query или fragment не принимаются.
3. Для пустого значения система должна показать «Укажите URL репозитория»; для другого хоста — «Поддерживаются только репозитории GitHub»; для прочих неверных значений — сообщение с допустимым примером URL. До исправления анализ не создаётся, введённый текст сохраняется.

Проверка приёмки: пустая строка, произвольный текст, SSH-ссылка, URL другой платформы и ссылка на файл отклоняются; ссылка на корень публичного репозитория с внешними пробелами, .git или завершающим слешем проходит проверку формата.

### FR-02. Проверка доступности публичного репозитория

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: синтаксически допустимый URL GitHub.

1. Перед запуском анализа система должна проверить, доступен ли указанный [Публичный репозиторий](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9F%D1%83%D0%B1%D0%BB%D0%B8%D1%87%D0%BD%D1%8B%D0%B9_%D1%80%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D0%B9) для чтения без личных учётных данных GitHub авторизованного или неавторизованного пользователя.
2. Если репозиторий не найден либо доступ запрещён, система должна показать «Публичный репозиторий недоступен», сохранить URL и предоставить его изменение. Запрос пароля или токена GitHub не предлагается, анализ не запускается.
3. Если проверка невозможна из-за временного сбоя или ограничения источника, система должна сообщить о временной недоступности и предоставить действия «Повторить» и «Изменить URL». Повтор выполняет проверку доступности заново.

Проверка приёмки: публичный доступный репозиторий допускается к дальнейшей обработке; отсутствующий/приватный — нет; временный сбой не отображается как доказанное отсутствие репозитория.

### FR-03. Получение актуального результата анализа

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: проверенный URL доступного публичного репозитория GitHub и команда «Анализировать».

1. Система должна проверить наличие актуального [отчёта](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) для репозитория у текущего владельца, определённого по проверенной сессии: аккаунта либо действующей гостевой сессии. Повторное использование допускается только при подтверждённом совпадении [состояния репозитория](https://ai.nsu.ru/projects/repopulse/wiki/%D0%A1%D0%BE%D1%81%D1%82%D0%BE%D1%8F%D0%BD%D0%B8%D0%B5_%D1%80%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D1%80%D0%B8%D1%8F), используемого периода оценки и методики с сохранённым результатом. Одного совпадения commit SHA недостаточно, если результат зависит от платформенных или зависящих от времени данных.
2. При подтверждённой актуальности система должна открыть существующий отчёт с его исходной датой и сообщением «Показан ранее сформированный актуальный отчёт», не создавая новый анализ или дубликат отчёта.
3. При отсутствии отчёта, изменениях либо невозможности подтвердить актуальность система должна принять новый [анализ](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%BD%D0%B0%D0%BB%D0%B8%D0%B7), присвоить ему идентификатор и открыть его состояние. Пока запрос этой формы обрабатывается, повторная отправка блокируется.

Проверка приёмки: новый репозиторий создаёт анализ; неизменившиеся исходные данные при той же методике и периоде возвращают прежний отчёт; изменившиеся Git/API-данные или период оценки приводят к новому анализу.

### FR-04. Просмотр состояния анализа

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: идентификатор принятого системой [анализа](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%BD%D0%B0%D0%BB%D0%B8%D0%B7).

1. Система должна показывать репозиторий, идентификатор анализа и одно из состояний: «Ожидание», «Выполняется», «Завершён», «Ошибка».
2. Во время ожидания и выполнения система должна обновлять состояние и предоставлять ручное действие «Проверить статус». Известный этап показывается; при отсутствии подтверждённого прогресса показывается индикатор выполнения без процента.
3. После успешного завершения система должна открыть отчёт именно этого анализа. Обновление страницы состояния должно восстанавливать тот же анализ, а не создавать новый.

Проверка приёмки: последовательность ожидание — выполнение — завершение ведёт к соответствующему отчёту; обновление страницы не меняет идентификатор анализа; при неизвестном прогрессе нет вымышленного процента.

### FR-05. Обработка неуспешного анализа

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Условие: принятый системой [анализ](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%BD%D0%B0%D0%BB%D0%B8%D0%B7) завершился неуспешно.

1. Система должна показать состояние «Ошибка», репозиторий, идентификатор анализа и понятную причину; если причина не определена — сообщение «Не удалось завершить анализ».
2. Система должна предоставить «Повторить анализ» и «Изменить URL». Повтор заново проверяет доступность репозитория и при её подтверждении создаёт новый анализ; прежняя ошибка не превращается в успешное завершение. Изменение URL возвращает форму с прежним значением для редактирования.
3. Ошибка не должна отображаться как готовый отчёт. Авторизованному или неавторизованному пользователю не выводятся stack trace, служебные учётные данные и секреты.

Проверка приёмки: принудительная ошибка анализа показывает указанные действия; повтор после восстановления доступности получает новый идентификатор; возврат к форме сохраняет исходный URL.

### FR-06. Восстановление просмотра после потери связи

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Условие: открыт принятый [анализ](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%BD%D0%B0%D0%BB%D0%B8%D0%B7), но запрос его состояния не получил ответ из-за сбоя связи.

1. Система должна показать сообщение «Не удалось обновить статус» и последнее подтверждённое состояние с отметкой времени его получения. Сбой запроса сам по себе не переводит анализ в состояние «Ошибка».
2. Система должна предоставить действие «Повторить проверку статуса». После восстановления связи она должна запросить результат по прежнему идентификатору и показать полученное состояние либо отчёт.
3. Восстановление просмотра не должно автоматически отправлять запрос нового анализа.

Проверка приёмки: разрыв связи при выполняющемся анализе не объявляет его неуспешным; после восстановления открывается состояние или результат того же анализа без дубликата.

### FR-07. Отображение объекта и времени анализа

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: принадлежащий текущему аккаунту или действующей гостевой сессии [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82).

1. При открытии отчёта система должна показывать платформу GitHub, владельца и название репозитория, ссылку на репозиторий, дату и время завершения анализа с часовым поясом.
2. Система должна показывать анализируемую ветку и commit SHA, если они определены; для неопределённых значений выводится «Не определено», а не предположенное значение.
3. Сведения должны относиться к сохранённому результату, не подменяться текущими данными репозитория. Авторизованный или неавторизованный пользователь должен иметь возможность открыть исходный репозиторий по показанной ссылке.

Проверка приёмки: данные отчёта совпадают с анализировавшимся репозиторием и ревизией; последующее изменение репозитория не меняет дату и ревизию сохранённого отчёта.

### FR-08. Отображение общей оценки

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) с результатами расчёта.

1. Система должна показывать рассчитанный [Repo Health Score](https://ai.nsu.ru/projects/repopulse/wiki/Repo_Health_Score) числом в диапазоне от 0 до 100 и текстовое объяснение основных факторов результата.
2. Если итоговая оценка не рассчитана, система должна вместо числа показать «Недостаточно данных для общей оценки» и причину. Отсутствие оценки не заменяется нулём, а доступные результаты категорий остаются доступны.
3. Рядом с общей оценкой система должна показывать предупреждение об ограничениях, если результат основан на неполных данных, и пояснение, что Score является первичной технической оценкой, а не гарантией качества или безопасности.

Проверка приёмки: рассчитанное значение отображается вместе с объяснением; результат без Score не показывает 0; неполный результат явно отличается от полного.

### FR-09. Просмотр оценок по категориям

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) с результатами по направлениям анализа.

1. Система должна показывать [категории оценки](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9A%D0%B0%D1%82%D0%B5%D0%B3%D0%BE%D1%80%D0%B8%D1%8F_%D0%BE%D1%86%D0%B5%D0%BD%D0%BA%D0%B8) для истории изменений, документации, наличия тестов, CI/CD и безопасности данных. Дополнительные результаты по зависимостям, версионированию, pull requests и code review показываются, если включены в выполненный анализ.
2. Для каждой категории система должна показывать название, рассчитанный балл от 0 до 100 либо состояние «Нет данных»/«Неприменимо», а также объяснение оценки или причину её отсутствия.
3. Авторизованный или неавторизованный пользователь должен иметь возможность выбрать категорию и просмотреть её показатели и основания выводов. Если направление разбито методикой на несколько категорий, они показываются с названиями, позволяющими определить соответствующее направление.

Проверка приёмки: все пять обязательных направлений представлены даже при отсутствии данных; дополнительное направление не появляется как проверенное без результата анализа; выбор категории показывает относящиеся к ней данные.

### FR-10. Просмотр оснований оценки

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) с показателями выбранной категории.

1. Для каждого использованного показателя система должна показывать название, измеренное значение с единицей измерения либо результат проверки «Обнаружено»/«Не обнаружено», а также объяснение его связи с оценкой.
2. Для агрегата система должна показывать период наблюдения и размер выборки. Если вывод получен сравнением с правилом или порогом, система должна показывать применённое правило или порог.
3. Система должна показывать подтверждающий факт и доступный источник: путь к файлу, commit, pull request, review или CI-запуск. Если для источника доступна ссылка, авторизованный или неавторизованный пользователь может открыть её; отсутствие ссылки не должно приводить к созданию вымышленного адреса.

Проверка приёмки: авторизованный или неавторизованный пользователь может сопоставить показатель с фактом; агрегат отображается с периодом и выборкой; сравнение с порогом раскрывает порог, реально использованный в анализе.

### FR-11. Просмотр обнаруженных проблем

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: доступный [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) с результатами обнаружения проблем.

1. Система должна показывать список [проблем](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9F%D1%80%D0%BE%D0%B1%D0%BB%D0%B5%D0%BC%D0%B0). Для каждой проблемы показываются название, категория, описание, критичность, подтверждающее основание и возможное последствие.
2. Система должна располагать проблемы в порядке уменьшения критичности: критическая, высокая, средняя, низкая, информационная. При равной критичности используется порядок названий категорий, затем названий проблем.
3. Если проблем не обнаружено, система должна показать «По выполненным проверкам проблемы не обнаружены». При неполных данных рядом выводится ограничение охвата, а не утверждение об отсутствии любых проблем в репозитории. Потенциальные находки обозначаются как потенциальные, а не как подтверждённые нарушения.

Проверка приёмки: список содержит основания и упорядочен по критичности; пустой список отличается от недоступного результата проверки; предположение не представлено доказанным фактом.

### FR-12. Просмотр рекомендаций по улучшению

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) с подготовленными рекомендациями.

1. Система должна показывать для каждой [рекомендации](https://ai.nsu.ru/projects/repopulse/wiki/%D0%A0%D0%B5%D0%BA%D0%BE%D0%BC%D0%B5%D0%BD%D0%B4%D0%B0%D1%86%D0%B8%D1%8F) конкретное предлагаемое действие, основание, ожидаемый эффект и приоритет, а также связь с проблемой или наблюдением из того же отчёта.
2. Рекомендации должны отображаться в порядке заданного приоритета. При одинаковом приоритете используется порядок названий рекомендаций. Авторизованный или неавторизованный пользователь должен иметь возможность перейти к соответствующей проблеме или наблюдению в отчёте.
3. При отсутствии рекомендаций система должна показать «Для этого отчёта рекомендации не сформированы». Предлагаемое действие не отображается как уже выполненное, ожидаемый эффект — как гарантированный результат.

Проверка приёмки: каждая рекомендация имеет объяснимое основание в отчёте; переход ведёт к этому основанию; пустой набор и предложения об исправлении отображаются без ложного утверждения об исправленном репозитории.

### FR-13. Отображение ограничений анализа

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) или [неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) со сведениями о доступности данных.

1. Система должна различать для показателей состояния «Данные получены», «Данные получены частично», «Данные недоступны» и «Неприменимо».
2. Для частичных, недоступных и неприменимых данных система должна показывать причину рядом с затронутым показателем и включать её в сводный раздел «Ограничения анализа», указывая затронутую категорию и ограниченный вывод.
3. Неизвестное значение не должно отображаться как ноль, подтверждённое отсутствие тестов/CI/review или доказанное отсутствие проблем. Подтверждённое проверкой отсутствие объекта должно отображаться отдельно от невозможности проверки.

Проверка приёмки: недоступная история CI и подтверждённое отсутствие конфигурации CI имеют разное представление; частичная выборка помечена; причина видна как у показателя, так и в сводке ограничений.

### FR-14. Сохранение результата в истории профиля

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) с определённым системой профилем. Событие: успешно завершён новый анализ этого авторизованного пользователя.

1. Система должна сохранить [отчёт](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) в истории [профиля авторизованного пользователя](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9F%D1%80%D0%BE%D1%84%D0%B8%D0%BB%D1%8C_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8F), определённого при запуске анализа, вместе с идентификатором анализа, репозиторием, датой и временем, анализировавшимся состоянием и полученными результатами. Истечение сессии после запуска не меняет принадлежность результата; для его просмотра требуется действующая сессия соответствующей учётной записи.
2. Повторное получение одного и того же завершённого результата не должно создавать дубликат записи. Новый анализ того же репозитория должен сохраняться отдельной записью, не перезаписывая прежний отчёт. Результаты гостевой сессии не добавляются в историю аккаунта при регистрации или входе.
3. Незавершённые и неуспешные анализы не должны появляться в истории как готовые отчёты. Сохранённый отчёт должен оставаться доступен после закрытия страницы и следующего открытия того же профиля.

Проверка приёмки: завершённый анализ появляется в истории один раз; следующий анализ добавляет новую запись; повторное открытие профиля сохраняет обе записи и их исходное содержимое.

### FR-15. Просмотр истории отчётов

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Условие: система определила текущий [профиль авторизованного пользователя](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9F%D1%80%D0%BE%D1%84%D0%B8%D0%BB%D1%8C_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8F); авторизованный пользователь открывает «Историю отчётов».

1. Система должна показывать только отчёты текущего профиля от новых к старым по времени завершения анализа. Для каждого показываются владелец и название репозитория, дата и время анализа, общий Score либо отметка «Оценка не рассчитана» и действие «Открыть отчёт».
2. Для пустой истории система должна показать «У вас пока нет отчётов».
3. И при заполненной, и при пустой истории система должна предоставлять действие «Новый анализ», открывающее форму URL.

Проверка приёмки: отчёты другого профиля в списке отсутствуют; порядок соответствует времени анализа; отсутствие Score не скрывает отчёт; из пустой истории доступен запуск нового анализа.

### FR-16. Открытие сохранённого отчёта

Актор: [Авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Вход: идентификатор выбранного сохранённого [отчёта](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9E%D1%82%D1%87%D1%91%D1%82) и текущий профиль.

1. Система должна проверить принадлежность отчёта текущему профилю и открыть именно выбранный результат с его исходными данными и датой, без повторного анализа репозитория.
2. Если отчёт отсутствует или не принадлежит профилю, система должна показать «Отчёт недоступен» без раскрытия его содержимого и предоставить возврат в историю.
3. Для открытого отчёта система должна предоставлять «Проверить снова». Это действие отправляет URL того же репозитория на новую проверку доступности и актуальности; простое открытие отчёта такую проверку не запускает.

Проверка приёмки: выбор старого отчёта показывает старый результат, даже если репозиторий изменился; запрос чужого идентификатора не раскрывает отчёт; новая проверка выполняется только по явному действию авторизованного пользователя.

### FR-27. Гостевая сессия и идентификация владельца отчёта

Акторы: [Неавторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%9D%D0%B5%D0%B0%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C) и [авторизованный пользователь](https://ai.nsu.ru/projects/repopulse/wiki/%D0%90%D0%B2%D1%82%D0%BE%D1%80%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9_%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C). Условие: использование RepoPulse в гостевой сессии либо аккаунте.

1. Неавторизованный пользователь без аккаунта должен иметь возможность запустить анализ публичного GitHub-репозитория и открыть свой отчёт в гостевой сессии без ввода личного GitHub-токена.
2. Система должна предоставлять регистрацию с непустыми login/password и вход по этим данным. Пароль скрыт при вводе, не возвращается в ответе и не попадает в отчёт. Пустые поля не отправляются; при занятом login регистрация не создаёт дубликат.
3. При неверных данных входа выводится «Неверный логин или пароль», пользователь остаётся неавторизованным. После успешного входа авторизованному пользователю доступна история текущего аккаунта. Успешная регистрация сама по себе не создаёт отчёт.
4. Владелец анализа определяется системой по проверенной гостевой сессии или аккаунту; переданный клиентом чужой user_id не меняет владельца.
5. Вход в аккаунт не переносит гостевые отчёты в историю. Гостевые отчёты остаются доступны только исходной действующей гостевой сессии. После истечения или утраты сессии чужой контекст не получает доступ.
6. История доступна только авторизованному пользователю в своём аккаунте. Открытие сохранённого отчёта не запускает новый анализ и сохраняет исходную дату/снимок.

Проверка приёмки:

- Неавторизованный пользователь без учётных данных GitHub запускает анализ и читает собственный результат; другая сессия не получает его.
- Пустые поля, повторный login и неверный пароль не создают аккаунт или авторизованную сессию соответственно.
- Два аккаунта видят разные истории; подстановка чужого report_id не раскрывает содержимое.
- Вход после гостевого анализа не добавляет гостевой отчёт в историю аккаунта.
