# Пользовательские сценарии и функциональные требования RepoPulse

Статус: согласование MVP  
Основание: Vision RepoPulse и задача Redmine #17655  
Область: первая версия веб-сервиса для анализа публичных Git-репозиториев

## 1. Цель документа

Документ описывает целевых пользователей, основной и альтернативные сценарии, состояния интерфейса и требования к результату анализа. Он служит общей основой для UX-прототипа, frontend, backend и проверки MVP.

## 2. Границы MVP

В MVP пользователь передаёт URL публичного репозитория GitHub. RepoPulse получает Git-данные и доступные данные GitHub API, выполняет анализ и формирует объяснимый отчёт.

В первой версии поддерживается только GitHub. Платформа задаётся в приложении статически; выбор другой платформы пользователю не предлагается.

Обязательные направления анализа MVP:

- историю изменений;
- документацию;
- наличие тестов;
- конфигурацию и доступные результаты CI/CD;
- безопасность данных.

Необязательные направления, которые могут быть добавлены при наличии готовой реализации:

- зависимости;
- версионирование;
- процесс внесения изменений через pull request или merge request;
- наличие и доступные результаты code review.

Вне MVP: приватные репозитории, подключение GitHub-аккаунта или пользовательского токена, изменение содержимого репозитория, интеграции с task tracker и внешними базами знаний, постоянный мониторинг и уведомления.

## 3. Целевые пользователи и цели

| Пользователь | Основная цель | Критерий ценности |
|---|---|---|
| Разработчик или владелец репозитория | Понять техническое состояние проекта и приоритет исправлений | За несколько минут получает объяснимую оценку и конкретный план улучшений |
| Team lead или технический руководитель | Быстро оценить незнакомый либо давно не проверявшийся проект | Видит общий риск, слабые категории и подтверждающие данные без полного ручного аудита |
| Участник open-source-проекта | Оценить зрелость проекта перед использованием или вкладом | Понимает активность, качество процесса изменений и основные технические риски |
| Преподаватель или проверяющий | Единообразно провести первичную проверку учебного проекта | Получает структурированный отчёт, но сохраняет за собой итоговое экспертное решение |

RepoPulse является инструментом первичной технической оценки. Итоговый балл не заменяет аудит безопасности, code review или экспертную оценку проекта.

## 4. Предусловия и бизнес-правила

1. Репозиторий должен быть публичным репозиторием GitHub и быть доступным без учётных данных пользователя.
2. Пользователь не передаёт токены, пароли или SSH-ключи.
3. Все оценки должны быть объяснимыми: балл связан с категорией, наблюдениями и конкретными данными репозитория.
4. Недоступные данные явно помечаются как `unavailable` или `not_applicable`; отсутствие данных нельзя автоматически выдавать за плохое состояние без правила оценки.
5. Отчёт фиксирует время анализа и идентификатор анализируемого состояния репозитория, если платформа или Git позволяют его получить.
6. Предыдущие отчёты сохраняются в профиле пользователя.
7. Перед новым анализом сервис проверяет, изменилось ли состояние репозитория с момента последнего сохранённого отчёта.

## 5. Основной пользовательский сценарий

### US-01. Получить отчёт о публичном репозитории

**Актор:** любой целевой пользователь.  
**Триггер:** пользователь хочет оценить техническое состояние репозитория.  
**Предусловие:** пользователь знает URL публичного репозитория.

1. Пользователь открывает главную страницу RepoPulse.
2. Сервис показывает краткое описание, поле URL, указание на поддержку GitHub и кнопку «Анализировать».
3. Пользователь вставляет URL публичного репозитория.
4. Интерфейс удаляет пробелы по краям и выполняет первичную проверку непустого значения и формата URL.
5. Пользователь запускает анализ.
6. Сервис повторно проверяет URL на сервере и доступность публичного репозитория GitHub.
7. Сервис определяет текущее состояние репозитория и сравнивает его с состоянием в последнем сохранённом отчёте.
8. Если репозиторий не изменился, сервис возвращает последний отчёт без нового анализа.
9. Если репозиторий изменился или отчёта ещё нет, сервис создаёт анализ и возвращает его идентификатор.
10. Интерфейс открывает `/analysis/:id`, блокирует повторную отправку того же запроса и показывает текущее состояние.
11. Сервис получает содержимое и историю через Git, доступные данные pull requests, review и CI/CD — через GitHub API.
12. Сервис рассчитывает оценки категорий и общий Repo Health Score.
13. После успешного завершения интерфейс открывает `/report/:id`.
14. Новый отчёт сохраняется в профиле пользователя.
15. Пользователь видит данные репозитория, общий балл, оценки категорий, объяснения, проблемы и рекомендации.
16. Пользователь может открыть исходный репозиторий, перейти к истории отчётов или запустить анализ другого репозитория.

**Постусловие:** в профиле пользователя доступен актуальный отчёт. Новый отчёт создаётся только при отсутствии предыдущего отчёта или при изменении репозитория.

### US-02. Открыть предыдущий отчёт

1. Пользователь открывает свой профиль.
2. Сервис показывает список ранее сформированных отчётов.
3. Пользователь открывает выбранный отчёт либо переходит к запуску нового анализа.

## 6. Альтернативные сценарии

### ALT-01. Пустой URL

1. Пользователь оставляет поле пустым либо вводит только пробелы.
2. Интерфейс не отправляет запрос.
3. Под полем отображается сообщение «Укажите URL публичного Git-репозитория».
4. Фокус остаётся или возвращается в поле URL.

### ALT-02. Некорректный URL

Некорректными считаются как минимум: не-URL строка, неподдерживаемая схема, URL без хоста или без идентификатора репозитория.

1. Интерфейс показывает сообщение «Введите корректный URL репозитория».
2. Анализ не создаётся.
3. Пользователь может исправить значение без потери введённого текста.

Сервер повторяет проверку независимо от frontend и возвращает машинный код `INVALID_REPOSITORY_URL`.

### ALT-03. Репозиторий недоступен

Причины: репозиторий не существует, удалён, приватный, доступ запрещён либо платформа временно недоступна.

1. Сервис не начинает содержательный анализ или безопасно прекращает его.
2. Интерфейс объясняет, что публичный репозиторий не удалось получить.
3. Пользователю доступны действия «Изменить URL» и, для временной ошибки, «Повторить».
4. Приватность репозитория не должна приводить к запросу токена в MVP.

Машинные коды: `REPOSITORY_NOT_FOUND_OR_PRIVATE`, `REPOSITORY_UNAVAILABLE`, `UPSTREAM_RATE_LIMITED`, `UPSTREAM_TIMEOUT`.

### ALT-04. Платформа не поддерживается

1. URL синтаксически корректен, но не относится к GitHub.
2. Анализ не создаётся.
3. Интерфейс сообщает, что первая версия поддерживает только публичные репозитории GitHub, и предлагает изменить URL.

Машинный код: `UNSUPPORTED_PLATFORM`.

### ALT-05. Анализ завершился ошибкой

1. Анализ уже был создан, но один из обязательных этапов завершился ошибкой.
2. Статус меняется на `failed`.
3. Интерфейс показывает понятное сообщение без stack trace и внутренних секретов.
4. Пользователь может повторить анализ или вернуться к вводу URL.

Машинные коды: `CLONE_FAILED`, `ANALYSIS_FAILED`, `REPORT_GENERATION_FAILED`, `INTERNAL_ERROR`.

### ALT-06. Потеря сети у пользователя

1. Интерфейс не меняет состояние анализа на ошибочное без ответа сервера.
2. Показывается сообщение о проблеме соединения и действие «Повторить проверку статуса».
3. После восстановления связи состояние запрашивается по тому же `analysisId`; новый анализ автоматически не создаётся.

### ALT-07. Не все платформенные данные доступны

1. Репозиторий и обязательные Git-данные доступны, но отдельный API-сигнал получить нельзя.
2. Сервис продолжает анализ, если правила расчёта допускают это.
3. В отчёте соответствующий показатель помечается как `unavailable` с причиной.
4. Пользователь видит ограничение рядом с категорией и в разделе «Ограничения анализа».

### ALT-08. Репозиторий не изменился после предыдущего анализа

1. Сервис находит в профиле пользователя предыдущий отчёт для этого репозитория.
2. Текущее состояние репозитория совпадает с состоянием, зафиксированным в отчёте.
3. Новый анализ и новый отчёт не создаются.
4. Пользователю открывается существующий отчёт.

## 7. Состояния интерфейса

| Состояние | Обязательное отображение | Доступные действия |
|---|---|---|
| Ввод URL | описание сервиса, поле URL, поддерживаемые платформы | запустить анализ |
| Ошибка валидации | сообщение рядом с полем, сохранённое значение | исправить URL |
| Создание анализа | блокировка повторной отправки, индикатор | дождаться ответа |
| `queued` | анализ принят, идентификатор анализа | вернуться на главную без отмены анализа |
| `running` | текущий этап или нейтральный индикатор, время последнего обновления | обновить состояние автоматически или вручную |
| `completed` | переход к итоговому отчёту | открыть отчёт |
| `failed` | понятная причина, код для поддержки, если есть | повторить или изменить URL |
| Потеря сети | состояние неизвестно, анализ не объявляется неуспешным | повторить запрос статуса |
| История отчётов | список предыдущих отчётов пользователя | открыть отчёт или запустить новый анализ |

Для MVP допустим polling статуса. Интервал должен исключать параллельные запросы и избыточную нагрузку; рекомендуемый UX-интервал — 2–5 секунд с увеличением при длительном анализе.

## 8. Что приложение отдаёт пользователю

Итоговый отчёт должен отвечать на четыре вопроса: **что анализировалось, насколько здоров репозиторий, почему получилась такая оценка и что делать дальше**.

### 8.1. Информация о репозитории

- платформа (`github`);
- канонический URL;
- владелец/namespace и название;
- описание, если доступно;
- default branch;
- идентификатор состояния: commit SHA анализируемой ветки, если доступен;
- время запуска и завершения анализа;
- версия схемы отчёта;
- ограничения и недоступные источники данных.

### 8.2. Общая оценка

- `Repo Health Score` — целое число от 0 до 100;
- краткая текстовая интерпретация;
- краткое объяснение главных факторов результата;
- сведения о полноте данных и ограничениях анализа.

### 8.3. Оценки по категориям

Для каждой применимой категории возвращаются:

- идентификатор и название;
- балл категории, если он рассчитан;
- состояние данных: `available`, `unavailable` или `not_applicable`;
- причина недоступности для состояния `unavailable`;
- краткое объяснение оценки;
- положительные и отрицательные наблюдения;
- доказательства: измеренное значение, файл/путь, URL объекта платформы или иной источник, если применимо.

Обязательные категории MVP: история изменений, документация, тесты, CI/CD и безопасность данных. Зависимости, версионирование, процесс pull requests и code review являются необязательными.

### 8.4. Обнаруженные проблемы

Каждая проблема содержит:

- стабильный идентификатор;
- категорию;
- заголовок и понятное описание;
- критичность: `critical`, `high`, `medium`, `low` или `info`;
- подтверждающие данные;
- путь или ссылка на связанный объект, если безопасно и доступно.

Список должен поддерживать однозначную сортировку по критичности, затем по категории.

### 8.5. Рекомендации

Каждая рекомендация содержит:

- стабильный идентификатор;
- приоритет;
- конкретное действие;
- ожидаемый эффект;
- ссылки на связанные проблемы;
- ориентировочную сложность (`small`, `medium`, `large`), если методика умеет её обосновать.

Рекомендации не должны утверждать, что проблема исправлена, пока RepoPulse только анализирует репозиторий.

Правила формирования рекомендаций определяются при проектировании ML-сервиса рекомендаций и не задаются этим документом.

### 8.6. Машиночитаемый результат

Frontend получает JSON, достаточный для всех перечисленных экранов. Минимально он содержит:

- идентификаторы анализа и отчёта;
- статус анализа и безопасное описание ошибки, если она возникла;
- сведения о репозитории и анализируемой ревизии;
- общий score, объяснение и сведения о полноте данных;
- категории с оценками, наблюдениями и доказательствами;
- проблемы и рекомендации;
- время анализа и версию схемы отчёта.

Состав результата согласован с JSON-моком и TypeScript-типами в `docs/ui`. Пользовательский экран не обязан показывать все технические поля, но обязан сохранять смысл, объяснимость и ограничения результата.

## 9. Функциональные требования

| ID | Требование | Проверка |
|---|---|---|
| FR-01 | Сервис принимает URL публичного репозитория и проверяет его на frontend и backend | пустой/невалидный URL не создаёт анализ |
| FR-02 | Первая версия поддерживает только публичные репозитории GitHub | URL другой платформы получает `UNSUPPORTED_PLATFORM` |
| FR-03 | Валидный доступный URL создаёт анализ с уникальным `analysisId`, если репозиторий новый или изменился | клиент переходит на `/analysis/:id` |
| FR-04 | Сервис предоставляет состояния `queued`, `running`, `completed`, `failed` | состояние доступно после обновления страницы |
| FR-05 | Завершённый анализ связан с одним итоговым отчётом | `completed` содержит `reportId` или URL отчёта |
| FR-06 | Отчёт содержит сведения о репозитории и Repo Health Score 0–100 | обязательные поля валидируются схемой |
| FR-07 | Отчёт содержит обязательные категории и доступные необязательные категории с доказательствами | каждая выведенная оценка объяснима наблюдениями |
| FR-08 | Отчёт содержит обнаруженные проблемы и рекомендации | элементы связаны с категорией и, где возможно, между собой |
| FR-09 | Недоступные данные отображаются явно и не маскируются нулём | категория имеет статус и причину |
| FR-10 | Ошибки имеют стабильный машинный код и безопасное пользовательское сообщение | UI не показывает stack trace или секреты |
| FR-11 | После сетевого сбоя UI продолжает проверять существующий анализ | новый анализ без действия пользователя не создаётся |
| FR-12 | Пользователь может изменить URL или повторить временно неуспешный запрос | действие доступно на экране ошибки |
| FR-13 | Отчёт фиксирует время, состояние репозитория и версию схемы | результат можно сопоставить с текущим состоянием репозитория |
| FR-14 | Предыдущие отчёты хранятся в профиле пользователя | пользователь может открыть старый отчёт или запустить новый анализ |
| FR-15 | Перед анализом сервис проверяет изменения репозитория | без изменений возвращается предыдущий отчёт, при изменениях создаётся новый |

## 10. Нефункциональные требования интерфейса

- Все состояния должны быть понятны без знания терминов Git API.
- Ошибка обозначается не только цветом; интерактивные элементы доступны с клавиатуры.
- Индикатор выполнения не должен показывать выдуманный процент, если backend не возвращает подтверждённый прогресс.
- Внешние ссылки на репозиторий открываются безопасно и визуально отличаются от внутренних действий.
- Технические сообщения логируются на сервере, а пользователю возвращается безопасный код обращения.
- Валидация frontend повышает удобство, но не заменяет серверную проверку.
