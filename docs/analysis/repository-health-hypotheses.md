## 1. Цель исследования

Цель исследования - определить признаки, по которым можно оценивать техническое состояние Git-репозитория, сформировать проверяемые гипотезы и выбрать набор метрик для MVP RepoPulse.

RepoPulse не должен оценивать репозиторий по одной характеристике: одна и та же метрика может иметь разный смысл в зависимости от контекста проекта и сочетания с другими показателями.

## 2. Определение «здорового» репозитория

Для RepoPulse предлагается использовать следующее определение:

> **Технически здоровый Git-репозиторий** - это репозиторий, который находится в поддерживаемом состоянии, способен устойчиво принимать и проверять изменения, имеет приемлемые риски безопасности и сопровождения, а процесс разработки не создаёт очевидных узких мест или критической зависимости от отдельных участников.

## 3. Существующие подходы

Для формирования гипотез были рассмотрены следующие известные подходы:

- **CHAOSS** - набор метрик для анализа состояния open-source-проектов и процессов разработки,
- **OpenSSF Scorecard** - набор автоматических проверок, в первую очередь связанных с безопасностью и практиками разработки,
- исследования по анализу GitHub и Git-данных, показывающие, что отдельные GitHub-метрики могут быть неоднозначными и требуют контекста,
- **DORA** - подход к оценке эффективности процесса поставки программного обеспечения. В актуальной модели DORA используются пять метрик: время прохождения изменения от коммита до production, частота поставки, время восстановления после неудачного изменения, доля изменений, приводящих к сбою, и доля внеплановой работы по исправлению проблем. Для RepoPulse важен прежде всего принцип совместной интерпретации показателей скорости и стабильности, а не прямой перенос DORA в модель Health Score.

## 4. Категории технического состояния

В соответствии с постановкой задачи для RepoPulse выделяются 9 категорий:

1. **Активность и регулярность разработки**
2. **Распределение изменений между участниками**
3. **Документация**
4. **Тестирование**
5. **Зависимости**
6. **Безопасность**
7. **CI/CD-конфигурация**
8. **Версионирование и релизы**
9. **Структура и организация репозитория**

Контекст проекта не является отдельной категорией и не получает собственного веса. Он используется для корректной интерпретации остальных показателей. Например, один основной разработчик может быть нормальным для личного проекта, а отсутствие CI может иметь разное значение для учебного и командного проекта.

## 6. Совместные метрики и комплексные сигналы

Во избежание «плоской» оценки RepoPulse предлагается использовать комбинации нескольких показателей.

### 6.1. Концентрация разработки

**Гипотеза:** высокая активность сама по себе не означает устойчивый процесс разработки. Если большая часть изменений выполняется одним участником и независимое review используется редко, процесс сильнее зависит от одного человека.

Используются: частота изменений, доля изменений крупнейшего участника, число активных участников, независимое review и self-merge.

| Сочетание | Интерпретация |
|---|---|
| Высокая активность + изменения распределены + большинство изменений проходит независимое review | Активная разработка сопровождается распределением участия и независимой проверкой |
| Высокая активность + большая доля изменений одного участника + высокий self-merge | Разработка и принятие изменений сосредоточены у одного участника |
| Один основной участник + review другим участником | Разработка сосредоточена у одного участника, но существует независимая проверка |

Комплексный сигнал не следует применять автоматически для личных и однопользовательских проектов.

### 6.2. Нестабильные автоматические проверки

**Гипотеза:** активная разработка при частых неуспешных запусках CI может указывать на проблемы в коде, тестах или инфраструктуре.

Используются: активность, наличие CI, доля успешных запусков, наличие тестов и запуск тестов в CI.

| Сочетание                                            | Интерпретация                                                                |
| ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| Активная разработка + высокая доля успешных проверок | Изменения регулярно проходят автоматические проверки                         |
| Активная разработка + низкая доля успешных проверок  | При активном развитии проверки часто завершаются ошибкой                     |
| Тесты есть + тесты не запускаются в CI               | Тестовая инфраструктура существует, но не включена в автоматическую проверку |
|                                                      |                                                                              |

### 6.3. Возможное снижение поддержки

**Гипотеза:** длительное отсутствие изменений само по себе не означает, что проект заброшен. Более убедительным признаком является сочетание отсутствия изменений с накоплением необработанных задач или PR.

Используются: время с последнего изменения, изменение активности, количество открытых issues/PR и доступные данные о времени ответа.

| Сочетание | Интерпретация |
|---|---|
| Давно нет изменений + нет открытых задач, требующих реакции | Данных недостаточно, чтобы считать проект заброшенным |
| Давно нет изменений + накапливаются открытые issues/PR без ответа | Есть признаки снижения активности сопровождения |
| Давно нет изменений + открытые задачи регулярно получают ответы | Низкая частота изменений может соответствовать стабильному режиму сопровождения |

## 7. Показатели, требующие данных GitHub/GitLab

Следующие данные невозможно получить только из `git clone` и истории Git:

1. Доля PR/MR, прошедших независимое review.
2. Доля self-merge.
3. Число уникальных ревьюеров.
4. Время до первого ответа ревьюера.
5. Результаты запусков CI/CD.
6. Обязательность прохождения CI перед merge.
7. Настройки защиты основной ветки.
8. Данные issues: количество открытых задач, возраст задач, время до первого ответа и закрытия.
9. Фактическая активность Dependabot/Renovate: созданные и объединённые PR.
10. Данные Community Profile, если они используются.
11. Информация о релизах платформы.

**Fork/Star/Watcher-активность** предлагается использовать только как контекстные показатели масштаба/популярности проекта, а не как самостоятельные показатели технического здоровья.

## 9. Конкретный набор метрик для MVP

MVP должен включать минимальный набор показателей, который имеет понятный источник данных, может рассчитываться воспроизводимо, реализуем для GitHub и GitLab и допускает корректную обработку отсутствующих данных.

| Категория | Метрики MVP | Источник |
|---|---|---|
| **1. Активность и регулярность** | Частота коммитов, дни с последнего коммита, изменение активности | Git |
| **2. Распределение изменений** | Доля крупнейшего участника, число активных участников, независимое review, self-merge, число ревьюеров, время до первого review, branch protection | Git + GitHub/GitLab API |
| **3. Документация** | README, основные supporting-файлы, актуальность документации | Git |
| **4. Тестирование** | Наличие тестов | Git |
| **5. Зависимости** | Доля зависимостей с более новыми версиями, автоматизация обновлений | Git + package registries |
| **6. Безопасность** | Известные уязвимости зависимостей, поиск секретов, наличие SAST-конфигурации | Git + vulnerability/security tools |
| **7. CI/CD** | Запуск тестов в CI, доля успешных CI-запусков, обязательность checks | Git + GitHub/GitLab API |
| **8. Версионирование и релизы** | SemVer tags, CHANGELOG/release notes | Git + GitHub/GitLab API |
| **9. Структура и организация** | `.gitignore`, типичные служебные файлы, базовая ecosystem-specific структура | Git |

Если источник данных недоступен, метрика получает `N/A`, а не 0. Отсутствие данных не является доказательством плохого состояния.

## 11. Предлагаемая модель Health Score

Текущий документ фиксирует гипотезу о расчете score. Окончательный метод, нормализация, веса и роль AI выбираются позже после согласования с другими аналитиками, бэкендом.
Health Score должен быть конкретным числом от 0 до 100, но не должен рассчитываться напрямую из отдельных исходных метрик.
### 11.1. Оценка категорий

Каждая оцениваемая категория получает значение от 0 до 100: $S_i \in [0,100]$
Для получения значения категории её отдельные показатели сначала нормализуются в диапазон от 0 до 100, после чего объединяются с заданными весами.

### 11.2. Предварительные веса

| Категория                 | Вес |
| ------------------------- | --: |
| Активность и регулярность | 15% |
| Распределение изменений   | 15% |
| Документация              | 10% |
| Тестирование              | 10% |
| Зависимости               | 10% |
| Безопасность              | 15% |
| CI/CD                     | 10% |
| Версионирование и релизы  |  5% |
| Структура и организация   | 10% |

Это стартовая гипотеза, а не эмпирически подтверждённые коэффициенты. В следующей задаче веса следует проверить на реальных репозиториях.
Если в категории часть метрик недоступна, итоговая оценка рассчитывается по доступным метрикам с перенормированными весами.

### 11.3. Формулы непрерывного оценивания показателей

Для перевода сырых значений показателей в баллы категории используются непрерывные функции. Это позволяет избежать дискретных скачков оценки и более плавно отражать изменения в состоянии репозитория.

В формулах могут быть использованы следующие типы функций:
- **Линейная нормализация:** $f(x) = \min(1, \frac{x}{X_{max}})$ - для метрик, где важно достичь определённого порога.
- **Логарифмическая:** $f(x) = \frac{\ln(1 + x)}{\ln(1 + X_{plateau})}$ - для метрик «чем больше, тем лучше», где после определённого значения рост перестаёт быть значимым (насыщение).
- **Экспоненциальный спад:** $f(x) = e^{-\frac{x}{k}}$ - для метрик «чем меньше, тем лучше» (время, количество проблем), где $k$ — коэффициент затухания.
- **Долевая:** $f(x) = x$ - для метрик, которые уже являются долями или процентами от 0 до 1.
### 11.4. Комплексные сигналы
После расчёта базового показателя применяются штрафы за подтверждённые сочетания проблемных показателей (комплексные сигналы из раздела 6). Штрафы применяются как коэффициенты снижения, а не как абсолютные значения, что позволяет избежать отрицательных итоговых оценок.

**Формула применения штрафов**:

$$HealthScore_{final} = HealthScore_{base} \cdot (1 - P_{total})$$
- $P_{total} = \min(0.5, \sum_{i=1}^{n} p_i)$ — суммарный коэффициент штрафа
- $p_i$ — коэффициент i-го применённого штрафа
- Максимальный суммарный штраф ограничен 50% (коэффициент 0.5, вообще сильно меньше по идее)

Необходимо помнить, что некоторые показатели будут являться штрафами сами по себе и вместе в комплексными штрафами будут штрафовать за один показатель повторно. Во избежание, коэффициенты комплексных штрафов должны быть небольшими. После оценки на реальных данных коэффициенты должны быть подкорректированы.
## 12. Ограничения модели

При интерпретации результатов необходимо учитывать:

1. **Тип проекта.** Учебный, личный, библиотечный и командный проекты могут иметь разные нормальные показатели.
2. **Размер проекта.** Один основной разработчик может быть нормальным для небольшого проекта.
3. **Жизненный цикл.** Завершённый проект может иметь низкую текущую активность без каких-либо проблем.
4. **Автоматизация.** Боты могут создавать большое количество коммитов и PR.
5. **Особенности платформы.** Часть данных доступна только через API GitHub/GitLab.
6. **Наличие метрики не означает наличие качества.** Например, README может существовать, но быть устаревшим.
7. **Один показатель не должен определять весь Health Score.**
8. **Пороговые значения и веса являются гипотезами.** Их необходимо проверять на наборе реальных репозиториев.

## 13. Итоговые гипотезы

Основные гипотезы RepoPulse:

1. **Активность и устойчивость разработки:** регулярность и динамика изменений, а также распределение вклада между участниками могут использоваться для оценки поддерживаемости проекта.
2. **Процесс разработки и code review:** независимая проверка изменений может снижать вероятность того, что ошибки или спорные изменения попадут в основную ветку без проверки.
3. **Тестирование и автоматические проверки:** наличие тестов и их автоматический запуск позволяют систематически проверять изменения.
4. **Зависимости и безопасность:** устаревшие или уязвимые зависимости, секреты и отсутствие автоматических проверок безопасности могут увеличивать технические и безопасностные риски.
5. **Документация и организация:** наличие базовой документации и понятной структуры может облегчать использование и сопровождение проекта.
6. **Версионирование и релизы:** формальное версионирование и описание релизов помогают отслеживать изменения между версиями.
7. **Комплексные сигналы:** сочетание нескольких показателей информативнее отдельных метрик и позволяет уменьшить количество ложных выводов.
