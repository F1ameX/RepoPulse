# Анализ платформенных данных GitHub и GitLab для RepoPulse

## 1 Возможности API GitLab и GitHub для публичных репозиториев

Проанализированы 11 публичных репозиториев: 6 на GitHub и 5 на GitLab. Выборка включает проекты разного размера и с разными процессами разработки.

GitHub предоставляет REST API для pull request, reviews, comments и GitHub Actions. Для публичных репозиториев основные данные доступны без авторизации, но **лимит составляет 60 запросов в час на IP; с токеном лимит существенно выше.**

GitLab предоставляет REST API для merge request, discussions, approvals, pipelines и jobs. Базовые сведения публичных проектов обычно доступны без авторизации, но **состав approval-данных зависит от настроек экземпляра, версии и тарифного уровня**. Для устойчивого сбора желательно использовать токен даже при работе только с публичными проектами.

Итог наблюдения:

- основные сведения о PR/MR найдены во всех 11 из 11 репозиториев;

- пригодная для анализа история CI/CD найдена в 9 из 11;

- review-данные технически доступны на обеих платформах, но на GitLab явное одобрение отображалось только в 4 из 5 проверенных проектов;

- отсутствие одного типа события нельзя автоматически считать отсутствием процесса: часть проектов использует внешние системы, комментарии вместо формального approval или отдельные CI-инструменты.

## 2 Сведения о PR и MR

| Сведение из задачи | Доступность в выборке | Польза для RepoPulse | Вывод |
| --- | --- | --- | --- |
| Количество PR/MR | 11/11 | Показывает поток изменений и позволяет сравнивать периоды | Использовать только вместе с размером команды и периодом |
| Статус open/closed/merged | 11/11 | Позволяет разделять активные, принятые и отклоненные изменения | Обязательное поле MVP |
| Дата создания | 11/11 | Основа для возраста и времени прохождения PR/MR | Обязательное поле MVP |
| Дата закрытия | 11/11 | Нужна для закрытых без merge и общего времени обработки | Обязательное поле, может быть пустым |
| Дата merge | 11/11 через API | Дает точное время принятия изменения | Не заменять датой последнего обновления |
| Незавершённые и долго открытые PR/MR | 11/11 | Выявляет накопление очереди и возможные блокировки | Порог должен рассчитываться относительно истории репозитория |
| Автор | 11/11 | Нужен для подсчета участников и разделения внутренних/внешних вкладов | Не применять для оценки отдельных людей |

В 90-дневном окне на GitHub число созданных/слитых PR заметно различалось: FastAPI — 375/167, Django — 459/127, Flask — 68/3, Requests — 47/15, TypeScript — 420/168, Go — 188/0. **Нулевое число merge у Go не означает отсутствие разработки: основной процесс рассмотрения изменений связан с внешней системой Gerrit. Это подтверждает необходимость отмечать применимость метрики.**

В небольшой выборке слитых PR медианное время до merge менялось от менее часа у Requests до примерно 734 часов у Flask. Для Flask в выборку попало только три merge, поэтому значение нельзя считать устойчивой нормой. Для GitLab по 20 последним MR медиана прокси-времени от создания до последнего обновления составила примерно от 3 часов у GitLab Runner до 176 часов у Omnibus GitLab. **В реализации это прокси использовать нельзя**: требуется точная пара created_at–merged_at.

Дополнительные сведения, полезные для корректной интерпретации:

<u>признак draft/WIP;</u>

<u>целевая и исходная ветки;</u>

<u>размер изменения и число коммитов;</u>

<u>labels;</u>

<u>связь с issue;</u>

<u>признак bot-автора;</u>

<u>конфликты и причина закрытия, если доступны.</u>

План данных PR/MR для RepoPulse: идентификатор, URL, платформа, репозиторий, автор, статус, draft, даты создания/закрытия/merge, возраст открытого PR/MR, длительность до merge/закрытия и агрегаты по выбранному периоду. Дополнительные поля используются как контекст, а не как самостоятельная оценка здоровья.

## 3 Сведения о code review

| **Сведение из задачи** | **Доступность в выборке** | **Польза для RepoPulse** | **Вывод** |
| --- | --- | --- | --- |
| Наличие review | API есть для 11/11 | Показывает, проходило ли изменение формальную проверку | Нужна оговорка: комментарий или внешний инструмент также могут быть review |
| Количество участников | Вычисляется для 11/11 при наличии событий | Показывает независимость и ширину проверки | Считать уникальных людей, исключая автора и ботов |
| Результат review | GitHub 6/6; явные approvals видны в 4/5 GitLab-проектов | Различает approval, запрос изменений и комментарий | Нормализовать платформенные статусы в общую модель |
| Комментарии и обсуждения | API есть для 11/11 | Показывает факт взаимодействия и объем обсуждения | Число комментариев не равно качеству review |
| Время до первого review | Вычисляется при наличии временной метки | Выявляет задержку начала проверки | Разделять первый комментарий, formal review и approval |

GitHub возвращает формальные review со статусами, включая approved, changes requested и commented, а также время отправки review. GitLab разделяет approvals, reviewers, notes и discussion threads. **В выборке GitLab явные approvals были видны у 4 из 5 проектов**; у F-Droid они были видны лишь у 4 из 20 просмотренных слитых MR. Это нельзя трактовать как отсутствие проверки без анализа обсуждений и правил проекта.

Дополнительные сведения:

- автор первого содержательного ответа;

- review от человека или бота;

- число нерешенных discussion threads;

- отменённые или устаревшие approvals;

- время от запроса review до первого ответа, если запрос фиксируется;

- наличие хотя бы одного проверяющего, отличного от автора.

План данных review: нормализованное событие с участником, типом результата, временем и принадлежностью к PR/MR; агрегаты — доля изменений с независимым review, медиана и P90 времени до первого review, медиана числа участников, доля изменений с нерешенными обсуждениями. При неполноте данных показатель получает статус «недостаточно данных», а не отрицательную оценку.

## 4 Сведения о CI и CD

| **Сведение из задачи** | **Доступность в выборке** | **Польза для RepoPulse** | **Вывод** |
| --- | --- | --- | --- |
| Наличие pipeline/workflow | Раздел или конфигурация обнаружены в 11/11 | Показывает наличие автоматизации | Наличие конфигурации не доказывает, что она проверяет каждый PR/MR |
| Статусы запусков | Пригодная история в 9/11 | Дает картину выполнения автоматических проверок | Нужна нормализация статусов |
| Успешные и неуспешные запуски | 9/11 | Основа для success rate и серий ошибок | Canceled/skipped учитывать отдельно |
| Длительность | 9/11 при завершенных запусках | Помогает выявлять замедление обратной связи | Сравнивать одинаковые workflow и типы событий |
| Последние результаты | 9/11 | Дает актуальный сигнал состояния автоматизации | Нельзя заменять исторический анализ одним последним запуском |

В просмотренной выборке GitLab CLI из 15 запусков имел 12 успешных, 1 неуспешный и 2 отмененных; F-Droid — 10 успешных, 4 неуспешных и 1 выполняющийся. У GitLab Runner большинство просмотренных запусков было успешным, также встречались ошибки и предупреждение. На GitHub Actions присутствовали во всех шести проектах, однако видимый верхний workflow не всегда представлял основной CI: например, у Flask среди последних запусков преобладала служебная задача блокировки обсуждений, а у Go основной процесс проверки изменений находится не только в GitHub.

Дополнительные сведения:

- имя workflow/pipeline и тип события запуска;

- ветка и SHA;

- связь запуска с конкретным PR/MR;

- время ожидания отдельно от времени исполнения;

- rerun/retry и номер попытки;

- обязательность проверки;

- статус отдельных jobs;

- признак внешнего CI.

План данных CI/CD: идентификатор запуска, PR/MR или commit, workflow, trigger, status, conclusion, created/started/finished timestamps, duration, attempt и URL. Агрегаты — success/failure/canceled rate, медиана и P90 длительности, серия последних ошибок и доля PR/MR с успешной проверкой до merge.

## 5 Гипотезы о состоянии процесса разработки

- **Накопление старых открытых PR/MR указывает на перегрузку обработки изменений.** Основание: одновременно растут очередь и возраст незавершенных работ.<br>

- **Рост времени до merge указывает на замедление потока изменений.** Основание: изменения дольше проходят обсуждение, проверки или ожидание решения.<br>

- **Низкая доля независимого review повышает риск недостаточной проверки.** Основание: автор остаётся единственным участником изменения.<br>

- **Большое время до первого review указывает на задержку обратной связи.** Основание: работа простаивает до начала проверки.<br>

- **Редкие или отсутствующие CI-запуски на PR/MR указывают на неполное автоматическое покрытие процесса.<br>**

- **Высокая доля неуспешных запусков указывает на нестабильность ветки, тестов или инфраструктуры.<br>**

- **Серия последних CI-ошибок является более срочным сигналом, чем единичный исторический сбой.<br>**

- **Merge без успешного связанного CI повышает риск попадания непроверенного изменения в целевую ветку.<br>**

- **Очень быстрый merge без review и CI может означать обход проверок.** Само по себе малое время положительно и становится риском только в сочетании с отсутствием контрольных событий.<br>

- **Расхождение между активностью репозитория и платформенными метриками может указывать на внешний процесс разработки.** Пример — использование Gerrit или внешнего CI.

## 6 Данные интерпретация и ограничения гипотез

| **Гипотеза** | **Необходимые сведения** | **Интерпретация** | **Ограничения и ложные срабатывания** | **MVP** |
| --- | --- | --- | --- | --- |
| 1. Старые открытые PR/MR | status, created_at, текущая дата, draft | Доля старых и P90 возраста выше исторической базы | Черновики, roadmap, ожидаемые внешние изменения | Да |
| 2. Рост времени до merge | created_at, merged_at, период | Медиана/P90 растут относительно прошлых периодов | Маленькая выборка, крупные изменения, релизный цикл | Да |
| 3. Нет независимого review | автор, review events, reviewers | Нет события от участника, отличного от автора | Review мог быть внешним или неформальным | Да, с confidence |
| 4. Медленный первый review | created_at или review_requested_at, первое review-событие | Время ответа выше собственной нормы репозитория | Неоднозначность первого содержательного события | Да |
| 5. CI не покрывает PR/MR | связь run–PR/MR, trigger, workflow | Низкая доля PR/MR с запуском проверочного workflow | Внешний CI или проверки после merge | Частично |
| 6. CI нестабилен | conclusion завершенных запусков | Высокий failure rate в сопоставимом workflow | Сбои инфраструктуры, экспериментальные workflow | Да |
| 7. Серия ошибок | упорядоченные последние conclusions | Несколько последовательных ошибок в основном workflow | Независимые ветки или разные причины | Да |
| 8. Merge без успешного CI | merged_at, связанный run, conclusion, commit SHA | До merge нет успешной обязательной проверки | API может не раскрывать required-checks; внешний CI | Частично |
| 9. Подозрительно быстрый merge | merge duration, review, CI | Быстрый merge одновременно без независимого review и успешного CI | Автомердж, документация, доверенные боты | Частично |
| 10. Внешний процесс | платформенная активность, ссылки и конфигурация проекта | Данные платформы не объясняют фактическую активность | Требуется ручное или дополнительное обнаружение интеграции | Только пометка |

Для всех гипотез пороги следует строить по собственной истории репозитория: медиана, P75/P90 и изменение между периодами. Универсальные жёсткие нормы допустимы только как стартовые значения до накопления истории.

## 7 Различия API GitLab и GitHub влияющие на RepoPulse

Назначение этого пункта — определить общую модель, которую можно одинаково наполнить с обеих платформ, и выделить места, где нужны разные адаптеры.

| **Область** | **Общее для платформ** | **Различия реализации** |
| --- | --- | --- |
| PR/MR | id, автор, state, created/closed/merged, draft, ветки | GitHub использует pull request и issue-связанные сущности; GitLab — merge request с IID внутри проекта |
| Review | участник, время, тип реакции, комментарии | GitHub имеет явные review states; GitLab разделяет approvals, reviewers, notes и discussions |
| CI/CD | запуск, workflow/pipeline, status, result, timestamps, commit | GitHub разделяет status и conclusion; GitLab использует собственный набор pipeline/job statuses |
| Связь CI с изменением | возможна через PR/MR, commit и branch | Способы связи и полнота полей различаются; нужен платформенный адаптер |
| Авторизация и лимиты | токен улучшает устойчивость | GitHub явно ограничивает анонимный REST 60 запросами/час на IP; GitLab зависит от экземпляра и его настроек |
| Дополнительные возможности | комментарии, pagination, фильтры | Approval rules, required checks и отдельные расширенные поля доступны неравномерно |

Общий внутренний формат RepoPulse должен хранить нормализованные сущности change_request, review_event и ci_run, а также исходную платформу, внешний идентификатор и URL. Извлечение, преобразование статусов и определение полноты данных выполняются отдельными GitHub- и GitLab-адаптерами.

<br><u>***</u><u>** **</u>Для MVP обязательно учитывать только те различия, без которых нельзя построить единую модель: разные способы получения PR/MR, представления review и approvals, нормализацию CI/CD-статусов и привязку запуска к изменению. Расширенные платформенные возможности — approval rules, required checks, merge queues и trains, подробные jobs/stages — **можно не учитывать для простоты**. Таким образом, отдельные адаптеры GitHub и GitLab нужны только для получения и преобразования базовых данных, а вся аналитика RepoPulse должна работать с единым внутренним форматом.

## 8 Минимальный набор платформенных данных для MVP

Для PR/MR:

- платформа, репозиторий, id и URL;

- author;

- state и draft;

- created_at, closed_at, merged_at;

- вычисленные age и time_to_merge/time_to_close.

Для review:

- PR/MR id;

- reviewer;

- нормализованный тип события: approved, changes_requested, commented;<br>**—**Если данные недоступны - data_completeness: partial/unavailable + причина. Технический unknown допустим только для РЕАЛЬНО неизвестного платформенного статус.

- event_at;

- признак независимости от автора;

- число участников и time_to_first_review.

Для CI/CD:

- PR/MR или commit SHA;

- workflow/pipeline name;

- Trigger;

- нормализованные status и conclusion;

- created_at, started_at, finished_at;

- Duration;

- URL.

Для корректной выдачи каждого показателя дополнительно нужны:

- source_platform;

- data_completeness: complete, partial, unavailable;

- confidence: high, medium, low;

- reason для неполных данных или неприменимости.

## 9 Предложения по требованиям к получению и отображению данных

- Система должна получать данные только через официальные API GitHub и GitLab с pagination и повтором временно неуспешных запросов.

- Система должна поддерживать токены обеих платформ и не считать анонимный режим гарантированным для регулярного сбора.

- Сырые платформенные статусы должны сохраняться вместе с нормализованными значениями.

- GitHub и GitLab должны обрабатываться отдельными адаптерами с единым выходным форматом.

- Даты должны храниться в UTC; длительности вычисляются только по подходящим временным меткам.

- Закрытый без merge PR/MR должен отличаться от merged.

- Draft/WIP не должен безусловно попадать в метрику просроченных изменений.

- Review автора и автоматического бота не должен считаться независимым review.

- Первый комментарий, formal review и approval должны храниться раздельно.

- Canceled, skipped, manual и running CI-запуски не должны смешиваться с failed.

- CI-метрики должны фильтроваться по workflow и trigger, чтобы служебные задачи не искажали оценку.

- Порог аномалии должен опираться на историю данного репозитория; при малой выборке показывается предупреждение.

- Интерфейс должен показывать значение, период, размер выборки, порог, направление отклонения и краткое объяснение.

- При внешнем или недоступном процессе система должна показывать «недостаточно данных» или «внешний процесс», а не отрицательную оценку.

## 10 Проекты Requirements для Redmine

### Requirement 1 Анализ PR и MR

RepoPulse должен получать из публичных репозиториев GitHub и GitLab PR/MR за выбранный период, сохранять их статус, автора и ключевые даты и рассчитывать количество созданных, открытых, закрытых и слитых изменений, возраст открытых изменений, медиану и P90 времени до merge. Draft/WIP учитывается отдельно. При малой выборке или признаках внешнего процесса результат помечается как ограниченный.

### Requirement 2 Анализ code review

RepoPulse должен получать формальные review, approvals, comments и discussions, приводить их к общей модели событий и рассчитывать долю PR/MR с независимым review, число уникальных участников, время до первого review и распределение результатов. Отсутствие формального approval не должно автоматически означать отсутствие review; при неполных данных вывод сопровождается уровнем уверенности.

### Requirement 3 Анализ CI и CD

RepoPulse должен получать workflow/pipeline runs и связанные с ними PR/MR или commits, нормализовать статусы, рассчитывать долю успешных и неуспешных завершенных запусков, медиану/P90 длительности, серии последних ошибок и долю PR/MR с успешной проверкой до merge. Служебные workflow, canceled, skipped и running учитываются отдельно.

### Requirement 4 Обработка недостаточных и неприменимых данных

Для каждой метрики RepoPulse должен хранить полноту и уверенность. Если процесс вынесен во внешнюю систему, API не предоставляет нужное поле или размер выборки недостаточен, система не формирует негативный вывод и отображает причину ограничения.

### Requirement 5 Объяснимое отображение платформенных метрик

Для каждого сигнала RepoPulse должен показывать текущее значение, анализируемый период, размер выборки, базовое значение или порог, статус отклонения и краткую интерпретацию. Пользователь должен иметь возможность перейти по ссылке к исходному PR/MR, review или CI-запуску.
