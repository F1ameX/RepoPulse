## Размещение и границы

`project/backend/internal/analyzer/application/scoring` — детерминированный модуль
Analyzer. Он создаёт три `MetricInput`, нормализует их и рассчитывает категорию
`activity`. Внешние источники, PostgreSQL и текущее системное время ему не нужны.

- `scoring.Default()` читает встроенный `config/rhs-mvp-1.1.0.json`, копию
  нормативного JSON №909. В ней пять категорий и 12 метрик, их относительные веса,
  параметры нормализации, пороги и версии. Не используется архивная локальная
  исследовательская модель девяти категорий.
- `scoring.Load(io.Reader)` загружает конкретную версию конфигурации. Отсутствующие
  или недопустимые веса/параметры, повторы и неизвестные метрики, лишние поля,
  неверное число категорий/метрик приводят к `domain.ErrInvalidData`.
- `Engine.Activity(t, window, versions, data)` преобразует подготовленные факты
  `ActivityData` в категорию с тремя входами, сырыми значениями, единицами,
  выборками, причинами и баллами. Входы для снимка берутся из `category.Metrics[].Input`.
- `Engine.ActivityFromInputs(t, window, versions, inputs)` считает ту же категорию
  по трём уже подготовленным входам контракта `MetricInput`.
- `Engine.ReplayActivity(snapshot)` повторяет расчёт по сохранённому снимку.
  Версии методики, конфигурации и профиля должны точно совпадать с загруженными;
  при несовпадении возвращается ошибка. Снимок не изменяется.
- `scoring.PublicScore(score)` округляет финальный балл до одного знака half-up.
  Вызывается только на границе публикации/отображения. Внутри модуля баллы,
  покрытие и агрегация не округляются; `null` сохраняется как `nil`, число 0 — как 0.

Полный Score пяти категорий и их фактические внешние веса — #18527. Сейчас
`Category.EffectiveWeight` остаётся `null`: общий знаменатель ещё не вычисляется.
Модуль не создаёт фиктивные остальные категории, находки или рекомендации.

## Данные от сборщика #18490

`ActivityData` — внутренний вход Go, а не новый HTTP/gRPC-контракт.

| Поле | Содержание и обязанность сборщика |
| --- | --- |
| `History` | `SourceState` для `git/history`; статус complete/partial/unavailable, при ограничениях обязательна причина. Общий статус истории сам по себе не доказывает полноту отдельного показателя. |
| `WindowCommits` | Число подтверждённых уникальных коммитов основной ветки в `[t−140 дней,t)`. Merge и боты включаются. При partial это известное число собранных коммитов, а не полный числитель частоты. |
| `LastCommitAt` | Наибольшее подтверждённое время committer основной ветки, включая коммит ровно в t. При полной пустой истории — nil. Дата после t или неизвестная дата — ошибка входа. |
| `LastCommitConfirmed` | Для неполной истории — отдельное доказательство, что последний коммит установлен. Одного коммита из прерванной/неупорядоченной выборки недостаточно. При complete отдельный флаг не нужен. |
| `Periods` | Счётчики только полных семидневных периодов, от старого к новому. Последний период заканчивается в t. Длина `p=min(20, число полных периодов возраста репозитория)`; периоды до возникновения репозитория не дополняются нулями. Пустой список и 20 нулевых недель — разные входы. |

Сборщик отвечает за SHA/refs, дедупликацию, определение основной ветки, возраст
репозитория, границы периодов и достаточность данных. Модуль не дублирует обход Git.
Он проверяет неотрицательность счётчиков, число периодов, согласованность их суммы
с окном, даты и статусы. Сборщик и интеграция сохранения/выдачи остаются #18490/#18491.

## Расчёты и снимок

Все интервалы фиксируются принятым `t`; новый вызов системного времени не делается.
Окно в каждом входе — принятые точные границы `[t−140 дней,t)` в UTC.

| Метрика | Сырой результат | Нормализация и сохраняемые основания |
| --- | --- | --- |
| `ACT_COMMIT_FREQ` | `WindowCommits / 20`, `commits_per_week` | `100*min(1,ln(1+x)/ln(11))`; sample numerator — число коммитов, denominator — 20 недель; collected/total — коммиты окна. |
| `ACT_DAYS_SINCE_LAST` | `floor((t−LastCommitAt)/24ч)`, `days` | `100*exp(−days/30)`; observed_at — committer UTC; sample collected/total — 1 подтверждённый последний коммит. |
| `ACT_TREND` | `R=sum(i*C[i+1])/sum(i*C[i])` при `i=1…p−1`, `ratio` | `50+50*tanh(ln(R)/ln(1.2)+0.5*ln(80/20))`; R=0 → 0 по пределу. series — недельные счётчики; sample numerator/denominator — взвешенные суммы, collected/total — число недель. |

При загрузке сохранённых входов числитель/знаменатель частоты, дата последнего
коммита и ряд тренда проверяются против `raw_value`; несогласованный или нечисловой
вход не превращается в ноль. Параметры формул и веса читаются из конфигурации.
`Metric.RuleVersion` сохраняет версию методики; версии конфигурации и профиля
остаются в `Snapshot.Versions` и `Report.Versions` существующего контракта.

Пустая полная история: частота и возраст — `not_applicable/NO_COMMITS_AT_ALL`;
тренд — `not_applicable/NO_COMMITS_IN_WINDOW`. История есть, но в окне 0 коммитов:
частота — число 0, возраст рассчитывается, тренд N/A. Другие причины тренда:
`INSUFFICIENT_PERIODS` и `ZERO_DENOMINATOR`.

При partial/unavailable истории частота имеет `raw_value=null`, сохраняет статус
и причину источника; collected может содержать известное число. Тренд — unavailable
с той же причиной, его неполный ряд не получает балл. Возраст без отдельного
подтверждения остаётся без балла; с подтверждением допускает complete. Это условие
явно задано в адаптере эталона ACT-06: опубликованные данные сами по себе не
доказывают последний коммит.

Категория — средневзвешенное только complete-метрик с фактически доступными
весами 0.35/0.35/0.30. Ноль входит в знаменатель, partial/N/A исключаются.
Нет вычисленных метрик — `score=null` с причиной; все метрики неприменимы —
`not_applicable`. Неполный состав категории — partial, покрытие — calculated/3.
Состояния partial/unavailable/not_applicable дополнительно подсчитываются отдельно.

## Подключение к Processor

После сбора истории Processor вызывает модуль с принятыми метаданными:

```go
engine, err := scoring.Default() // один раз при инициализации
if err != nil {
    return err
}
category, err := engine.Activity(analysis.AssessmentAt, analysis.Window, analysis.Versions, facts)
if err != nil {
    return err
}
// category.Metrics[].Input -> SnapshotData.Inputs вместе с входами других категорий
// category -> ReportData.Categories; публикация снимка/отчёта остаётся транзакционной
```

Штатный `cmd/analyzer` пока не получает готовый Processor от соседних задач.
Добавление этого модуля само по себе не включает completed-отчёт в Docker и не
заменяет сборщик либо Report Service. Для этого нужны #18490/#18491 и последующая
сборка Processor; существующее честное завершение без результата не меняется.

## Проверки

`go test -race ./internal/analyzer/application/scoring` проверяет семь опубликованных
ACT-эталонов 1.0.1, контрольные значения 7 коммитов/неделю, 100/e и R=1.6,
предел R=0, стабильность 80, N/A, отдельное подтверждение последнего коммита,
UTC/полные сутки, отрицательные и несогласованные входы, неверную конфигурацию,
повтор после JSON-сохранения снимка, неизменность входов и отсутствие промежуточного
округления. SHA в опубликованных JSON — синтетические метки, не настоящие Git SHA;
проверка реального сбора/границ/веток относится к #18490.
