# Backend-каркас: task-17661

Основание: предоставленный `repopulse_architecture.md` и задача подготовки
среды backend. Эта заметка фиксирует принятые в каркасе решения для ревью;
она не означает, что согласование с архитектором уже проведено.

## Стек и размещение

- Go 1.26.0+, стандартные `net/http`, `log/slog`, `testing`.
- Один Go-модуль в `project/backend`, рядом с существующим `project/frontend`.
- Первый исполняемый процесс — `cmd/api` (API Service / BFF).
- Внешняя граница — HTTP/JSON, версия API `/api/v1`, отдельный `/health`.
- Конфигурация — окружение процесса с проверкой значений при запуске.
- Локальный запуск — `go run ./cmd/api`; CI — GitHub Actions, gofmt, go vet, тесты и сборка.

Стандартной библиотеки достаточно для текущего HTTP-каркаса. Точки расширения
выделены по ответственности, чтобы выбор клиентов gRPC, Kafka и PostgreSQL
можно было сделать вместе с реализацией соответствующих сервисов.

## Соответствие целевой архитектуре

| Компонент | Состояние в этой задаче | Следующий этап |
| --- | --- | --- |
| API Service / BFF | HTTP-процесс, конфигурация, логи, health, три заглушки | JWT, валидация DTO, error mapping и gRPC-клиенты |
| Auth Service | Не реализован | Регистрация, сессии и выдача токенов |
| Analysis Orchestrator | Определены базовые статусы и этапы | Workflow, идемпотентность, outbox/inbox, состояния анализа |
| GitHub API Service | Зарезервирован пакет адаптера | API-клиент, нормализация и completeness снимков |
| Repository Sandbox Service | Не реализован | Изолированное клонирование и выполнение в gVisor |
| Analysis Service | Зарезервирован пакет анализаторов | Анализ снимков и данных sandbox |
| Scoring / Recommendation / Report | Не реализованы | Оценка, рекомендации и immutable отчёты |

API Service не обращается к БД, не запускает анализаторы и не клонирует
репозитории. Будущие доменные сервисы должны запускаться отдельными процессами.
Наличие пакетов в одном модуле не объединяет их ответственность в BFF.

Целевые ограничения из архитектуры сохраняются:

- синхронные межсервисные вызовы — gRPC;
- Kafka передаёт команды, события и идентификаторы результатов;
- полные снимки запрашиваются через gRPC у сервиса-владельца;
- у сервисов отдельные PostgreSQL database и DB user;
- Redis служит кэшем, PostgreSQL хранит достоверное состояние;
- доступ к отчёту проверяет Report Service, JWT проверяет API Service.

Реализация этих компонентов, proto-контрактов, миграций, JWT, метрик и полного
инфраструктурного стенда находится за пределами задачи каркаса. Текущие
`501`-ответы не открывают доступ к каким-либо доменным данным.

## Интеграционные решения для ревью

Backend резервирует `/api/v1/analyses` и `/api/v1/reports/{report_id}`.
По целевой архитектуре результат старта будет различать новый `analysis_id`
и уже существующий `report_id`, а статус анализа будет объектом.
Эти контракты подготовлены для согласования; интеграция frontend остаётся
отдельной задачей.

Формат успешного Report ещё требует отдельного решения: текущая UI-модель
в `project/frontend/src/types/index.ts` использует camelCase и вложенные
категории, а архитектурный документ задаёт логическую модель доменного Report.
При реализации Report Service/BFF нужно определить преобразование в UI-модель
либо одновременно обновить контракт и frontend. В этой задаче успешный ответ
отчёта не заявлен в OpenAPI и не имитируется.

Для ревью с архитектором и frontend подготовлена
[заметка об API](../api/backend-integration.md). Решения не требуют внешних
учётных данных для локальной проверки.
