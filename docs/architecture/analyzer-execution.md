# Исполнение очереди и безопасное чтение Git

Реализация [#18476](https://ai.nsu.ru/issues/18476), по архитектуре
[№916](https://ai.nsu.ru/documents/916) и профилю
[№889](https://ai.nsu.ru/documents/889). Формы данных остаются в
[контрактах](../../contracts/README.md), поля статуса — в
[AnalysisStatus](../fields/analyzer.md#analysisstatus).

## Что подключено

`cmd/analyzer` запускает очередь PostgreSQL и статический Git-коллектор.
Нормализаторы #18479 и последующие расчёты подключаются через `worker.Processor`
в `app.RunWithProcessor`. Интерфейс объявлен у потребителя — в
`internal/analyzer/application/worker`, реализации связываются в `app`.
Processor получает принятый Analysis, структурные GitData и ограниченный
ReadBlob; пути к рабочей копии ему не передаются.

Processor возвращает типизированные SnapshotData и ReportData. Метаданные
владельца, t/окна и версий хранилище берёт из принятого задания. Для optional
объяснения есть отдельный метод `worker.Explainer`; при его ошибке можно
сохранить заранее подготовленный deterministic_fallback. Сетевой AI-клиент
здесь не реализован.

В обычном `cmd/analyzer` Processor пока не подключён. После получения Git такое
задание заканчивается failed/ANALYSIS_FAILED без отчёта. Никаких фиктивных метрик
или результатов в production-процессе нет. HTTP-запуск и чтение состояния —
#18478; существующий CreateAccepted — внутренний вызов после проверки публичности,
а не готовый HTTP CreateAnalysis. Статус читается через storage.Get с проверкой Owner.

## Жизненный цикл

1. Принятое задание хранится в `analyzer.analyses` со статусом queued.
2. Claim короткой транзакцией выбирает старейшее queued-задание через
   `FOR UPDATE SKIP LOCKED`, выставляет running/collecting_git, started_at и
   deadline_at. Commit происходит до сетевого обращения. Один процесс исполняет
   одно задание; несколько процессов используют ту же очередь без брокера.
3. Git-коллектор фиксирует объявленные heads/tags. Уже известные branch/SHA не
   меняются; ранее неизвестные поля заполняются однократно через Pin.
4. Processor подтверждает collecting_external и calculating. Этапы не могут
   идти назад; повторы этапа допустимы. При подключённом Explainer исполнитель
   выставляет explaining, перед записью — saving. Процентов выполнения нет.
5. Пригодный полный/частичный результат проходит существующую валидацию
   Snapshot/Report. Снимок, отчёт и completed публикуются одной транзакцией.
   refs и полнота уже собранных Git scopes берутся у коллектора, а не заменяются
   утверждением Processor о полной выборке.
6. Если подтверждённых входов/находок нет — ANALYSIS_FAILED; ошибка публикации —
   REPORT_SAVE_FAILED; истечение общего срока — BUDGET_EXCEEDED.
   Ошибка хранится в AnalysisStatus.error, stage очищается.

Completed и failed неизменяемы. Чтения статуса и результата только читают БД.
Выполненный job не ставится заново в очередь. После аварии процесса незавершённый
running получает failed/BUDGET_EXCEEDED при следующей проверке просроченных
deadline_at; новое выполнение требует новой отправки пользователя.

Общий срок от started_at — до 320 с. Git входит в этот срок; основная обработка
заканчивается не позднее started_at + 300 с. Объяснение ограничено 20 с и остатком
общего срока с небольшим резервом для сохранения. При отмене/ошибке фиксация failed
имеет отдельный служебный таймаут 3 с. Если сама БД недоступна, running будет
завершён проверкой истёкшего срока после восстановления БД/исполнителя.

## Как читается Git

- Создаётся временный приватный bare-репозиторий без checkout. Нативный Git
  запускается с явными аргументами, без shell, системных/пользовательских config,
  credential helper, hooks, fsmonitor и шаблонов пользователя. Установка пакетов,
  сборка, тесты, фильтры и submodules исследуемого проекта не запускаются.
- Разрешены только публичные GitHub HTTPS-адреса принятого Repository.
  Нативный Git обращается к приватному loopback HTTP-адаптеру внутри того же
  процесса. Адаптер направляет только info/refs и git-upload-pack на фиксированный
  GitHub upstream, не передаёт авторизацию/cookie и не следует redirects.
  Он считает входящие байты потока и прерывает чтение на 100 MiB.
- Объявляются heads/tags, fetch получает именно их зафиксированные object SHA
  и принятый commit SHA. Shallow/filter не используются. Сдвиг удалённой ветки
  не подменяет уже выбранный SHA; недоступность объекта отражается ограничением.
- ls-tree читает до 50 000 путей дерева pinned commit; rev-list — до 10 000
  уникальных коммитов всех полученных refs и pinned commit. Main отмечает
  достижимость из основной ревизии. Сообщения/патчи коммитов в GitData не входят.
- ReadBlob использует cat-file без textconv/фильтров, максимум 1 MiB на blob и
  200 MiB суммарного чтения за job. Симлинк — blob с текстом назначения;
  переход по нему не выполняется. Processor обязан отразить ошибку чтения blob
  в ограничениях зависимого входа. Полный проход секретов по истории — #18524.
- Вся фаза получения Git и чтения дерева/истории в Open ограничена одним сроком
  60 с: fetch, cat-file, ls-tree и оба rev-list используют один контекст. Локальное
  чтение не получает новый бюджет после сети. Истечение срока отражается как
  GIT_TIME_LIMIT у затронутого scope, с неизвестным total и без fingerprint.
  Отдельная HTTP-попытка — 15 с, число Git
  HTTP-запросов — 20. Каждый дочерний процесс ограничен контекстом job;
  Linux/macOS при отмене завершают его группу процессов. Проверены macOS и
  Docker/Linux; групповой механизм отмены на Windows здесь не реализован.
- Git-объекты и сырые blob остаются временными. Close удаляет репозиторий
  до completed, а также при обычной ошибке/отмене. При жёстком убийстве процесса
  (SIGKILL) defer не исполняется; временный диск контейнера удаляется вместе
  с контейнером. stderr и содержимое исходников в логи не выводятся.

## Полнота и причины

GitData содержит Repository, refs, Files (path/mode/object SHA/size), Commits
(SHA/committed_at/Main), ReceivedBytes и SourceState scopes refs/tree/history.
Main=true подтверждается встреченным SHA в обходе основной ревизии;
Main=false допустим только после полного успешного обхода этой ревизии.
При усечённом/прерванном обходе отсутствие SHA означает Main=null, а не false.
Нормализатор активности должен сохранять эту неизвестность в полноте своих входов.
Это временные внутренние факты, не новый HTTP/gRPC DTO и не Snapshot.
Нормализатор переносит нужные безопасные факты в 12 MetricInput.

| Причина | Ограничение |
|---|---|
| GIT_SIZE_LIMIT / GIT_TIME_LIMIT | Прерван поток по байтам/времени |
| GIT_HTTP_LIMIT / GIT_REQUEST_LIMIT | Исчерпан лимит запросов/размер служебного запроса |
| GIT_FETCH_FAILED / GIT_FETCH_INTERRUPTED | Сбой получения или оборванный ответ |
| GIT_PATH_LIMIT / GIT_COMMIT_LIMIT | Выборка дерева/истории ограничена |
| GIT_REFS_INVALID / GIT_REVISION_UNAVAILABLE | Неполные refs или недоступная pinned ревизия |
| GIT_TREE_INVALID / GIT_TREE_INTERRUPTED | Не удалось полностью прочитать дерево |
| GIT_HISTORY_INVALID / GIT_HISTORY_INTERRUPTED | Не удалось полностью прочитать историю |
| GIT_BLOB_LIMIT / GIT_BLOB_UNAVAILABLE | Нельзя получить blob в пределах профиля |

У ограниченного источника status=partial/unavailable, reason заполнен,
Sample.total=null: известное collected не выдаётся за полный объём.
Независимые успешно прочитанные scopes могут оставаться complete.
Пустой полностью полученный репозиторий отличается от недоступного источника.
Только у complete scopes есть fingerprint зафиксированных SHA/refs.
Сам fingerprint не доказывает актуальность внешних GitHub/OSV наборов.

## Запуск и технические проверки

Из корня: `docker compose up -d --build`; затем `docker compose logs -f analyzer`.
Новые миграции не требуются: очередь, сроки, stage/error уже есть в foundation.
Git включён в backend runtime-образ. Параметры описаны в
[README backend](../../project/backend/README.md#переменные-окружения).

Из `project/backend`:

```sh
go test -race ./...
REPOPULSE_GITHUB_SMOKE=1 go test -run TestPublicGitHubSmoke -v ./internal/analyzer/adapter/out/git
```

Для интеграции очереди задайте REPOPULSE_TEST_DATABASE_URL тестовой PostgreSQL
с правом CREATE DATABASE, как в README backend. Проверяются конкурентные Claim,
терминальность, истёкшие сроки и однократная транзакционная публикация частичного
результата. Нормализованные данные этого теста — явно обозначенные fixtures;
они проверяют оркестрацию, а не готовность расчётов #18479.

Детерминированный Git-тест использует настоящий Git smart HTTP и контрольный
репозиторий с отдельной несмерженной веткой, тегом, симлинком, исполняемым файлом
и опасной пользовательской Git-конфигурацией. Проверяет отсутствие выполнения,
лимиты/обрыв, полноту, неизменность данных и удаление временного репозитория.
Отдельный opt-in smoke проверяет реальный публичный GitHub; обычные тесты
не требуют доступа к GitHub.
