1. **Cпособы получения данных публичного Git-репозитория 
по URL.**
---
**GitHub REST API**

Получение данных через HTTP-запросы к официальному REST API GitHub. Возвращает структурированные данные в JSON.
Можно получить:
- Историю коммитов;
- Ветки;
- Теги;
- Авторов и коммиттеров;
- Изменённые файлы в коммитах;
- Структуру файлов репозитория;
- Pull Requests, Issues, Reviews, Comments;
- GitHub Actions, workflow runs, jobs и checks.
- Содержимое файлов репозитория:

    На основе содержимого репозитория уже можно обнаружить и проанализировать:
  - README и другую документацию; 
  - конфигурации CI/CD; 
  - файлы зависимостей и lock-файлы; 
  - тестовые файлы; 
  - build- и конфигурационные файлы.

Основное преимущество — данные сразу приходят в структурированном виде и удобны для обработки сервисом.

https://docs.github.com/en/rest/repos/contents?apiVersion=2026-03-10

---

**GitHub GraphQL API**

Альтернативный официальный API GitHub. 

Основные отличия от REST API:

- можно запрашивать только необходимые поля, не получая лишние данные;
- связанные сущности можно получать вложенно в рамках одного запроса
- структура JSON-ответа заранее определяется структурой GraphQL-запроса; 
- API имеет строгую типизированную схему, описывающую доступные объекты, поля и связи между ними.

Например, для Pull Request одним запросом можно получить сам PR и связанные с ним commits, reviews и другие сущности, тогда как при использовании REST API для этого могут потребоваться отдельные запросы к нескольким endpoint'ам.

Основное преимущество — более гибкое получение связанных данных и возможность уменьшить количество запросов и объём передаваемой информации. 

Основной недостаток — запросы сложнее формировать и обрабатывать

---

**Git clone / Git protocol**

Получение локальной копии Git-репозитория через стандартный Git-протокол. После клонирования сервис работает
с локальной Git object database и файлами репозитория.

Основные отличия от REST API:
- после clone или fetch дальнейший анализ Git-данных выполняется локально; 
- GitHub-specific данные (Issues, Pull Requests, Reviews и workflow runs) получить нельзя.

Основной недостаток — сервис должен клонировать, хранить и обновлять локальные копии репозиториев, что увеличивает использование диска, сети и вычислительных ресурсов.

2. **Какие данные можно получить из Git**

Для MVP:

- история коммитов;
- метаданные коммитов:
  - SHA; 
  - родители; 
  - автор;
  - committer;
  - дата;
  - сообщение;

- ветки;
- теги;
- структура файлов и директорий;
- содержимое файлов;
- изменения между версиями:
  - changed files;
  - additions;
  - deletions;
  - diff;

- история изменений конкретного файла в упрощённом виде;
- обнаружение на основе структуры и содержимого:
  - README и документации;
  - CI/CD-конфигураций;
  - dependency manifests и lock-файлов;
  - тестовых файлов;
  - build-конфигураций;
  - используемых языков и технологий

После MVP для более глубокого анализа можно добавить:

- полный commit graph;
- анализ divergence веток(насколько ветки разошлись: сколько уникальных коммитов появилось в каждой после общей точки);
- merge commits;
- merge base между ветками;
- hotspots — файлы с высокой частотой изменений;
- ownership по файлам и директориям;
- stale branches(ветки, в которых долгое время не было новых коммитов.);
- анализ долгоживущих веток;
- анализ release cadence(частота и регулярность появления новых релизов/релизных тегов);
- анализ submodules(обнаружение подключённых через Git submodule внешних репозиториев и используемых их версий);
- история изменения зависимостей(когда зависимости добавлялись, удалялись или обновлялись);
- AST-анализ исходного кода;
- вычисление сложности кода(используя различные известные метрики);
- поиск дублирования;
- анализ покрытия тестами;
- анализ уязвимостей зависимостей.

**3. Ограничения при работе с внешними репозиториями**

Про все репозитори лимитс:
https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits


- Размер репозитория.
    Размер .git не превышает 10 GB, до 5000 веток,
    глубина директорий до 50 уровней, до 3000 элементов в одной директории.

- Время клонирования.
Для Git read operations (clone, fetch) рекомендуемый предел — около 15 операций в секунду на один репозиторий

- Недоступность репозитория. При обращении через GitHub REST API может возвращаться 404 Not Found, если репозиторий 
не существует или недоступен текущему пользователю. Также возможны 401 Unauthorized и 403 Forbidden для проблем с аутентификацией и правами доступа.

- Некорректный URL. Если URL содержит неверный owner/repository или указывает на несуществующий репозиторий, 
GitHub возвращает 404 Not Found. 

- Большой объём истории. см. пункт 2

- Бинарные и крупные файлы. Рекомендуемый максимальный размер одного Git-объекта — 1 MB, 
жёсткий лимит обычного файла — 100 MB. Для больших файлов GitHub использует Git LFS.Максимальный размер одного 
LFS-файла составляет от 2 GB до 5 GB.

- Подозрительные или потенциально опасные файлы. GitHub не гарантирует безопасность содержимого публичных репозиториев.

**4. Подход к ограничению времени и объёма анализа.**

- Ограничение времени анализа. 
Для каждого health-check задаётся общий timeout. По его истечении анализ принудительно завершается, а результат помечается как неполный.
- Ограничение времени клонирования. 
git clone / fetch имеет отдельный timeout, чтобы очень большой repository не блокировал весь анализ.
- Ограничение размера репозитория. Перед или во время загрузки контролируется объём данных. При превышении лимита 
полный анализ не выполняется либо переключается в сокращённый режим.
- Ограничение глубины истории. Анализировать не всю историю, а последние N коммитов или коммиты за заданный период, например последние 6–12 месяцев.
- Ограничение количества анализируемых файлов. Если repository содержит слишком много файлов, анализируется только ограниченное число либо файлы интересующих типов.
- Ограничение размера отдельного файла. Большие файлы не передаются в текстовый/AST-анализ; учитывается только их наличие и метаданные.
- Исключение бинарных файлов. Бинарные файлы не анализируются по содержимому.
- Ограничение объёма diff. Для очень больших коммитов можно не сохранять и не анализировать полный patch, 
а использовать только changed files, additions и deletions.
- Частичный результат. Если один из лимитов достигнут, уже собранные данные не отбрасываются.
В результате сохраняется analysis_status, например complete, partial, timeout, size_limit_exceeded.

**5. Какие операции недопустимо выполнять с исходным кодом анализируемого репозитория.**

- Выполнение исходного кода из репозитория;
- Запуск исполняемых файлов и скриптов;
- Запуск build-команд;
- Запуск тестов;
- Установка зависимостей без изоляции;
- Выполнение CI/CD-конфигураций;
- Передача коду токенов, ключей и других секретов;
- Изменение состояния RepoPulse или его внутренних ресурсов;
- Произвольные сетевые запросы со стороны анализируемого кода.
