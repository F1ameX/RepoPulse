# Единый контракт RepoPulse MVP

Контракты разделены по сервисам и редактируются как исходные спецификации.
HTTP API задаёт OpenAPI, поля JSON — сервисные JSON Schema, сообщения и методы
бинарного gRPC — `.proto`. Код классов каждый исполнитель получает своими инструментами.

| Пакет | JSON Schema | Protobuf |
|---|---|---|
| common | [Общие модели](common/v1/schemas.json) | [common.proto](common/v1/common.proto) |
| auth | [Сессии и реквизиты](auth/v1/schemas.json) | [AuthService](auth/v1/auth.proto) |
| analyzer | [Анализ и снимок](analyzer/v1/schemas.json) | [Сообщения Analyzer](analyzer/v1/analyzer.proto) |
| report | [Отчёт и история](report/v1/schemas.json) | [ReportService](report/v1/report.proto) |
| gateway | [HTTP OpenAPI](gateway/v1/openapi.json) | — |

[Описание всех полей JSON и gRPC](../docs/field-map.md) содержит типы,
номера protobuf, обязательность, допустимость null, значения и назначение полей.
[HTTP операции, параметры и соответствие вызовам](gateway/README.md).
[Движение данных от запроса до сохранённого отчёта](../docs/architecture/data-flow.md)
описывает обработку повторных отправок, переходы состояний, переиспользование
отчётов, сбор снимка и проверку зависимостей через OSV.

OpenAPI использует версию 3.1 и JSON Schema 2020-12, сервисные определения
подключены внешними `$ref`. В `.proto` используются proto3 optional и импорты
common/v1/common.proto. JSON и gRPC имеют отдельные представления данных;
Gateway переносит поля в HTTP DTO при реализации обработчиков.

Номера protobuf определены только в `.proto`. После публикации удалённые
номера и имена резервируются через reserved; переиспользовать их нельзя.
Несовместимые изменения имён, типов, обязательности и значений enum требуют
новой версии API. Версии методики и профиля независимы от API.

## Транспорт и границы

| Потребитель | Интерфейс |
|---|---|
| Frontend | HTTP `/api/v1/...`, схемы OpenAPI/JSON Schema |
| Gateway → Auth | gRPC `AuthService`: Register, Login, CreateGuestSession, ResolveContext, Logout |
| Gateway → Report | gRPC `ReportService`: GetReport, ListReports |
| Analyzer → Report | FindReusableReport с полным проверенным контекстом |
| Gateway → компонент Analyzer | Типизированный внутренний интерфейс `x-analyzer-interfaces`: ValidateRepository, CreateAnalysis, GetAnalysis |
| Analyzer → очередь/снимки/отчёты | PostgreSQL, сервисные каталоги `migrations/auth`, `migrations/analyzer`, `migrations/report` |

Analyzer — компонент backend с отдельным контрактным пакетом. Gateway вызывает
его типизированный внутренний интерфейс ValidateRepository/CreateAnalysis/GetAnalysis.
В `analyzer.proto` определены сообщения; транспорт gRPC предусмотрен для Auth и
Report. Сбор, пять анализаторов, Score и AI — модули Analyzer. Gateway занимается
HTTP, проверенным контекстом и передачей вызовов. Реализация pipeline — #18476
и следующие задачи.

Один публичный `Report`; `Snapshot` и `Owner` — внутренние модели, не альтернативные
DTO отчёта. Внешние тела запросов не принимают owner/user/session IDs.
Все неизвестные поля отклоняются, а не игнорируются.

## Обязательная сериализация

- HTTP JSON использует **snake_case**. Gateway переносит поля gRPC-сообщений
  в HTTP DTO и сериализует DTO в JSON.
- Обязательные поля всегда присутствуют. Неизвестные значения — `null`, списки
  без элементов — `[]`. `0`, `false`, `null` и отсутствующее поле различаются.
- Для скалярных полей с допустимым отсутствием используется `optional string`,
  `optional int32`, `optional double` или `optional bool`. В Go они представлены
  указателями: nil означает отсутствие, указатель на нулевое значение — его наличие.
  У полей-сообщений наличие отслеживается самим protobuf; raw_value — google.protobuf.Value.
- Идентификаторы GitHub — строки, UUID — строки UUID. int64 в JSON не используется.
- Времена — RFC3339 UTC `Z`. Точные границы окна сохраняются; формат UI до секунд
  не меняет исходную точность. Момент оценки `t` фиксируется на первую отправку,
  окно `[t−140 дней,t)`. При чтении отчёта даты не обновляются.
- Баллы 0..100 либо null. Расчёт без промежуточного округления, публичный балл и
  отображение — десятичное half-up до одного знака. UI не пересчитывает Score.
- Все пять категорий и 12 разных метрик присутствуют даже при N/A. Статусы данных:
  complete/partial/unavailable/not_applicable. Частичная выборка не выдаётся за полную.

## Владельцы и сессии

`VerifiedContext` создаёт только Auth на основании проверенных cookie. Он может
одновременно содержать аккаунт и исходный гостевой контекст по FR-27 ред. 3.0.1.
Новый запуск выбирает аккаунт, если он действителен; иначе действующего гостя.
Сохранённый `Owner` всегда ровно один и никогда не меняется при входе/выходе.
user_id/guest_session_id внутреннего VerifiedContext соответствуют auth.principals.id
с kind=account/guest; auth.sessions.id — отдельный внутренний ID записи реквизитов.
Для guest principal допускается одна session; для аккаунта — независимые сессии.
Чтение исходного гостевого результата допускается при сохранённой действующей
гостевой cookie даже после входа; история содержит только отчёты аккаунта.

Выбраны непрозрачные серверные сессии: `repopulse_session` и `repopulse_guest`,
HttpOnly/Secure/SameSite=Lax/Path=/api/v1. Это реализационный выбор для требований
сайта.
В БД сохраняются только хэши случайных токенов. Пароли хранятся как Argon2id
в формате PHC (`$argon2id$v=19$m=…,t=…,p=…$соль$ключ`); параметры задаются
конфигурацией Auth и записаны в каждом хэше, поэтому смена настроек не ломает
проверку старых паролей.

Аккаунт — ровно 168 часов без продления, persistent cookie до срока сессии.
Гость — максимум 24 часа и браузерная сессия; cookie без Max-Age/Expires.
На границе срока доступ уже прекращён. Logout отзывает текущую account session,
сохраняет независимые сессии и guest cookie; повтор безопасен. Создание гостя не
восстанавливает старые результаты. Сохранность cookie подтверждается следующим
GET /auth/session до запуска анализа.

Если account cookie предъявлена, но истекла/отозвана/недопустима, новая операция
не получает гостевого владельца автоматически: возвращается SESSION_EXPIRED
или SESSION_REQUIRED. «Продолжить как гость» — явное действие UI: безопасный
logout очищает account cookie, затем проверяется исходный действующий guest
либо создаётся новый. При действующем аккаунте истёкший guest не заменяет аккаунт.
Повтор CreateGuestSession при уже действующем guest возвращает тот же контекст
и исходный срок (200); создание нового — 201. Срок не продлевается.

Для cookie-запросов изменения состояния необходима проверка Origin/CSRF;
не допускаются wildcard credentialed CORS и передача cookie через URL.
Внутренние gRPC-контексты доступны только доверенным backend-вызовам; внешняя
достижимость внутренних RPC и защита соединений — обязанность конфигурации запуска.

Проверки логина/пароля и URL производятся после нормализации в порядке №888.
Raw JSON Schema намеренно не ограничивает длину URL до trim или пароля до NFC:
это изменило бы допустимые значения. Нормативный предел URL — 2048 code points
после удаления внешних U+0020. Login — ASCII 3..32 после trim, lowercase.
Пароль — 15..128 Unicode code points после NFC; U+0020 сохраняется, регистр значим,
разрешены L/M/N/P/S и U+0020; одни пробелы отклоняются. Эти семантические проверки
должны быть реализованы в клиенте и Auth; одна валидация JSON Schema их не заменяет.

## История и публикация результата

Analyzer сохраняет снимок + отчёт + status=completed одной транзакцией в общей
PostgreSQL. Таблицы разделены схемами auth/analyzer/report; Report отвечает за
чтение отчётов и историю. Порядок развёртывания задан в
[миграциях](../project/backend/migrations/README.md). Уникальность analysis_id
ограничивает число отчётов. Проверку владельца, переход в completed и
неизменяемость результата обеспечивает Analyzer.
История — проекция сохранённых account reports, отдельное событие её пополнения
не нужно. Порции до 20: completed_at DESC, report_id ASC. В начале просмотра
материализуется membership history_view_items, последующие курсоры привязаны к
этому view и владельцу. Один timestamp cutoff не защищает от позднего commit
другого отчёта; новые результаты появляются после обновления просмотра.

Миграция не включает готовые HTTP/gRPC обработчики, роль SQL не является
проверкой пользовательской сессии. Каждый обработчик проверяет сессию/владельца;
БД задаёт связи и уникальность записей.
[Сопоставление ошибок HTTP/gRPC](../docs/errors.md).
